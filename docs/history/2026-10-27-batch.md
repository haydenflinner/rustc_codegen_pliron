## Open: seed 13475, a slot-merging miscompile in the defaults

Batch-2 fuzz (13300–13699, 399/400 pass) found seed 13475: wrong output at
`-O0` (stock `hash: 5533973766801760215`, pliron `12153670319719403803`).
It is **not** a batch-2 flag. The seed fails with no flags set, and with
`COLDCOPY=0`, `REMATCALL=0` or both. It passes with every DEFAULT_ON flag
off, and with `PLIRON_SLOTMERGE=0`.

Turning default flags off one at a time:

- passes with any one of `SM_COALESCE=0`, `SM_BYSIZE=0`, `SM_FLOWIV=0`,
  `SM_STARTS=0`;
- still fails with `SLOTMERGE_MARK=0`, `SM_MARKFLOW=0`, `SM_PRECISE=0`,
  `SM_DROPNC=0`, `SM_AFTERKILL=0`, `SM_STARTONLY=0`, `SM_ESCFLOW=0`,
  `SM_COALCALL=0` or `NOCAP_FIELDS=0`;
- also fails with the inliner group or `DEADFREE` off.

So slot merging gives two slots one home while both are live. Each of the
four flags that hide it changes which pairs get merged, so this is a wrong
interference answer, not one bad flag. These defaults were turned on
2026-10-26 after 400 clean fuzz seeds (9700–10099) and clean UI and crate
runs. Seed 13475 is the first counterexample. The program and outputs are
saved under `target/harness/fuzz/13475`. Next: bisect to the function
(`harness/fnbisect.py`), dump the merge decisions, write a regression
test, and add 13475 to the gate's `FUZZ_REGRESS` together with the fix.
Until then, `PLIRON_SLOTMERGE=0` is the kill switch.

**Narrowed down at 08:20.** `harness/fnbisect.py` names one function,
`fn11` (14 runs; the program is saved as `tests/seed13475/p.rs.txt`). It is
small: a straight-line block that writes `[u8; 6]` locals, then
`dump_var(Move(_1), Move(_9), ..)` and `dump_var(Move(_5), Move(_6), ..)`.
`PLIRON_SM_INFO=all PLIRON_SM_INFO_FN=4fn11` prints `slotmerge nslots=16`,
`merge: 7 cand -> 2 regions`, and one edge kill:
`edge kill ss0 on inst193 (in block0) dest 4294967294`. That dest is
`BEFORE_INST`: ss0 dies just *before* inst193.

**Diagnosis (08:27, from the `PLIRON_CLIF=4fn11` dump before and after
slotmerge).** Before slotmerge, block0 does:

```
v24 = stack_addr ss12 ; v25 = stack_addr ss13
store v2, v24                    ; arg array -> ss12
copy 6 bytes ss12 -> ss13        ; load v24, store v25
store v5, ss9 ; copy ss9 -> ss10
store v8, ss5 ; v35/v36 = load ss5
...                               ; later the calls read ss13 (the moved array)
```

Slotmerge maps 15 of the 16 slots, ss13, ss9 and ss5 among them, onto
ss12, and deletes the now-self copy ss12 -> ss13. ss13 is still live
until the call reads it, but ss9's and ss5's stores now hit the same
bytes. So the call sees v8's bytes instead of the array.

**Which merge (08:30, `PLIRON_SM_LIMIT=n` with `PLIRON_OPT_FNS` on
fn11).** The output is good up to 4 merges and bad from 5. Merge 5 is the
copy-coalescing join (`SM_COALESCE`) of **ss13 into ss12's region**. It is
the only difference between 4 and 5: `v25 = stack_addr ss13` becomes
`ss12`. By then the region already holds ss0, ss1, ss5, ss9 and others.
ss13 is the home of `_3`, an argument array that fn11 overwrites with
constants four times and never reads in between.

An earlier draft of this section said coalescing tests only the source's
lifetime. That is wrong: the join adds the destination's segments to
`occ[r]`, and under `SM_STARTS` it tests the other members' starts and
segments (slotmerge.rs, the `coal.get(&s)` branch). The fault is in that
test's inputs. Either ss13's live segments are modelled too short (its
stores are all dead stores, so its "starts" are just store points), or
another member's segment is too short to contain ss13's stores. Next:
print `mine`, `ol` and `os` for that join (`PLIRON_SM_INFO=all`, add the
detail), and see which member is live across ss13's constant stores.
Regression test: fn11 itself, as a `test.sh` stanza with the dump_var
calls turned into prints.
