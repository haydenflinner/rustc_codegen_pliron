# Fuzz seed 16782: loadfwd kept a stop-named loc across a plain-name store

**Symptom.** The pliron `-O` build of rustlantis seed 16782 never finished
(more than 300 s; stock takes about 20 ms). `-O0` was fine. The bug was
already on main at 42b49c8.

## Narrowing

- `PLIRON_LOADFWD=0` finished. `PLIRON_DIFFCHECK=step` reported that
  `loadfwd2` on `fn10` turned a returning function into one that ran out of
  interpreter fuel. `clif-check pair before.clif after.clif` reproduced the
  mismatch. `clif-check step loadfwd2 before.clif` did not: the
  operand-frozen facts are not serialized (see the replay fidelity gap in
  `docs/miscompile-triage.md`).
- `PLIRON_OPT_FNS=~1p4fn10` plus `harness/bisect.py` gave unit 595,
  `loadfwd2` on `fn10`.
- The diff contained this forward:

  ```
  v32 = iadd v6, 24                   ; v6: noalias param
  store.i64 0x64c3_d97f_8b40_8150, v32
  ...
  store.i64 3, v6+24                  ; same bytes, plain name
  v439 = load.i64 v32                 ; forwarded 0x64c3..., should be 3
  brif (v439 >= 4) ... br_table v439  ; a loop's state dispatch
  ```

  `PLIRON_TRACE=pliron::loadfwd=debug` showed `load ... arg v2628 root
  V(v2628) off 0`. The address (`v32`, an alias in the real build) was its
  own root because it is an operand-frozen operand: a `stop` in `na`.

## Cause

loadfwd names memory two ways. Locs are keyed by the `na` root, where `na`
is `noalias` plus the `ofrozen` stops. `iso`/`ncc` are classified by the
`na0` (`noalias`-only) root. The store arms already kill a second time
under the store's `na0` name. That covers a store made *through* a stop
name. The reverse case was missing: a loc kept *under* a stop name and a
store through the plain name. `kill` compared `V(v2628)` with `(V(v6),
24)`, saw different roots, and kept the loc because `V(v6)` is `iso`.
`iso` only promises that no *untracked* pointer reaches `v6`'s memory, but
`v2628` is derived from `v6`. The stale value made the loop's exit test a
constant, so the loop never exited.

## Fix

`loadfwd::kill_stops`: after the existing kills, every store arm (plain
and `select`, in `transfer` and in `pre`'s scan) translates each loc keyed
under a stop-only name `V(x)` into `n0(x)` plus the loc offset. It then
tests that against the store's `na0` footprint. The same object reached
through two names counts as the store's own write, so it is killed by byte
overlap with no immunity, like `kill`'s `own`. Otherwise the loc keeps
`kill`'s rules: `!invariant.load`/region immunity, distinct slots, `iso`
and `ncc`. The extra pass over the locs runs only when there is a stop
name (`na.len() > na0.len()`). It is linear in the loc set, the same as
`kill`.

## Evidence

- Seed 16782 now prints the stock hash. Seed 16787 also passes.
- `pliron-clif-opt/tests/loadfwd_stop_name_store.rs` is the 7-line shape
  with `v2` frozen. Without the fix, diffcheck sees `returned 3` before and
  `returned 7` after. With the fix, the test passes.
- Seed 16782 is in `FUZZ_REGRESS` (`harness/gate.py`).
