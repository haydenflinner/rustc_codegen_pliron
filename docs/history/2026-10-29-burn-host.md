# 2026-10-29: Burn host build, and the depthwise weight-gradient "nondeterminism"

Recipe and tables: [`../cubecl-burn-host.md`](../cubecl-burn-host.md). This
file is the investigation log for part B (the owner's "nondeterministically
wrong depthwise conv weight gradients on Burn's CPU runtime") and the two
compiler bugs part A found.

## Verdict (part B)

**Not ours. A CubeCL bug (reached through Burn's depthwise fast path), already
fixed in cubecl `main`, not in the revs Burn pins.** It reproduces 100 % of the
time with a stock rustc host build and the stock LLVM JIT kernels; with a
pliron-compiled host it fails identically; with the one-condition cubecl fix it
passes 200/200.

Root cause: `conv_weight_grad_depthwise` folds the batch into the channels with

    reshape(permute(input, [1, .., rank-1, 0]), [1, ..spatial, C * N])

`reshape` of a permuted view cannot stay a view, so `burn_cubecl::ops::reshape`
falls back to `cubecl::std::tensor::copy_into(input, fresh_empty_output)`.
`copy_into` on a **CPU client** picks the "perpendicular" (transposing) kernel
when the input's last stride is not 1 and `input.rank == output.rank`:

```rust
let same_rank = input.strides.len() == output.strides.len();
if input.strides[rank - 1] != 1 && is_cpu && same_rank { launch_copy_perpendicular_ref(..) }
```

That kernel indexes the input with the output's coordinates, so it is only
correct when the two **shapes** are equal (a pure layout change). Here the rank
is 4 on both sides but the shapes differ (`[H, W, C, N]` vs `[1, H, W, C*N]`):
the copy scrambles the data and leaves part of the freshly `empty` output
unwritten. A fresh heap page reads as zeros; a reused allocation holds whatever
an earlier kernel left there. That is the "nondeterministic" part (uninitialised
reads, as the owner's commit message guessed), layered on a deterministic
indexing error.

Only the CPU runtime is affected (`is_cpu`), only rank-preserving reshapes of
permuted views, which is why the owner saw it on exactly this path and why GPU
CI is green.

Fix (cubecl-std `copy_into`): compare shapes, not ranks.

```diff
-    let same_rank = input.strides.len() == output.strides.len();
-    if input.strides[rank - 1] != 1 && is_cpu && same_rank {
+    let same_shape = input.shape == output.shape;
+    if input.strides[rank - 1] != 1 && is_cpu && same_shape {
```

cubecl `main` (68fa214) already has this (`let same_shape = input.shape ==
output.shape;`, with the comment "A reshape keeping the rank would otherwise
reach it and index the input out of bounds"); the revs Burn pins (`5e521ef`
for burn main 00a9db74c, `d0052727` for the owner's fork) do not. So the fix for
Burn is a cubecl pin bump past that change; until then the owner's per-group
workaround in `conv_weight_backward_fallback` is a valid local mitigation.

### What was ruled out on the way

- The folded convolution kernel (`conv_forward_nhwc` with `groups = C` on the
  `[1, H, W, C*N]` image): matches the ndarray reference, 15/15.
- Autotune picking a wrong candidate (my first suspicion for the nondeterminism):
  the failure is deterministic in *which elements* are wrong; autotune is not
  needed to explain it.
- A pliron miscompile: the failing set is identical for stock and pliron host
  builds, and a one-line cubecl change fixes both.
- The other owner commit ("empty 0-byte buffers", cubecl-matmul vector
  alignment): unrelated code paths (matmul / `into_vec_unchecked`); not touched.

# Part A compiler bugs found by building Burn

Two pliron-only failures, both fixed on main with regression tests.

## 1. rsasm: Mach-O `.pushsection` (`bfa5499`)

Symptom: ICE while compiling `burn-ndarray`'s dependency tree (the `ctor` /
`linktime` crates):

    assembling asm!/global_asm! failed: error: expected a string of section flags
    .pushsection __DATA,__ctor_force,regular,no_dead_strip

Cause: rsasm's generic `.pushsection` only parses the ELF operand form; its
Mach-O `.section` parser was not reachable through `.pushsection`.
Fix: `macho_directive` handles `.pushsection` (push the section stack, then the
Mach-O `SEG,SECT,type,attrs` parse). Test: `vendor/rsasm/tests/macho.rs`
`pushsection_takes_the_mach_o_operand_form` (fails without the fix).

## 2. jumpthread::round: args read through the edge's new bindings (`cb7f1bf`)

Symptom: `burn-fusion` lib tests: 5 of 139 fail under pliron only
(`a_failing_fused_kernel_errors_the_whole_block`, ...: a caught panic did not
claim the block's outputs).

Bisect (all numbers from this session):

1. `harness/fnbisect.py` over burn-fusion's 5876 functions: 16 runs ->
   `burn_fusion::stream::execution::scope::base::Work::claim::<String>`.
2. `harness/bisect.py` with `PLIRON_OPT_FNS` set to that symbol: 425 units in a
   full run; first bad unit 394 = step `jtround` on that function.
3. `PLIRON_CORPUS` + `clif-check pipeline` gave the pre-`jtround` CLIF;
   hand-reduced to a 4-block loop (`pliron-clif-opt/tests/jt_round_param_alias.rs`).
   `clif-check step jtround min.clif`: MISMATCH (before returns 999, after 11).

Cause: `round()` binds a merge block's params to the edge's args one at a time
into `env`, and looked the *next* arg up through that same `env`. On a back
edge into a loop header the args can be the header's own params (the previous
iteration's values: `block232(0, 0, 0, v1019, v1020, v1021)` where `v1019` is a
param of `block232`), so `v1019` read as the just-bound `v1019 = 0` and the
threaded `icmp eq v1019, 0` was decided the wrong way (a parallel-copy bug,
same family as the `edgespec` one in `tests/edgespec_loop.rs`).
Fix: evaluate args (`known`, `kbits`) against an empty outer env.
Test: `pliron-clif-opt/tests/jt_round_param_alias.rs` (fails without the fix).
Gate green before the push (83 jobs).
