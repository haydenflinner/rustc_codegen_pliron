# Compile time: syn and kernels-wasm profiles, two fixes (2026-10-27)

Baseline: main `f1ffe88`, release dylib, no `PLIRON_*` set, 14-core
Apple Silicon shared with other agents (load 8–14). Inputs and commands
are `harness/ctime.py`'s.

## Profile

### syn (16 CGUs, native rlib)

`/usr/bin/time`: 3.7 s wall, 20 s user; LLVM 3.4 s wall, 16 s user.
samply at 1 kHz (`harness/sprof.py`), 14.0 k samples:

| where | samples | note |
|---|---|---|
| rustc frontend + metadata (shared with LLVM) | ~2000 | 1.4 s single-threaded, incl. 0.33 s `collect_and_partition_mono_items` under `encode_metadata` |
| `cgupool::iropt_head` (stage A, serial per CGU) | 3628 (26%) | inline 1339 (`clone_blocks_into` 486), sroa 550, nocapture 548, phisimp 202, guardelim 192, nowrite 162 |
| CLIF pipeline (`run_pipeline`) | 5401 (39%) | flat: jumpthread 736, ifconv2 376, loadfwd 328, edgespec 248, mergechain 248, slp 232, licm 204, sameargs 306, slotmerge 182 |
| `FnLower::lower` (phase A, serial per CGU) | 896 (6%) | |
| cranelift `compile` | 679 (5%) | |
| allocator (`_rjem_*`, `zone_*`, memmove) | ~1100 (8%) | |

Per-CGU timeline (`PLIRON_TRACE_FILE` marks; its per-step appends
inflate the pipeline rows, so only the shape is trusted):

- all 16 CGUs submit within 0.47 s and start stage A at once;
- stage A of the biggest CGUs takes 1.0–1.2 s (cgu.04: sroa 203 ms,
  inline 150+119, nocap 113+41, callgvn 97, memcpyopt 74, nowrite2 70,
  earlydead2-free 64, sroa-fwd 64), then phase-A lowering 0.36 s;
- while the big CGUs are in stage A the pool runs 3–7 threads busy
  (`tline.py` buckets); when they lower, 11 threads; then an 0.8 s
  tail at 3–4 threads.

The tail is the long functions: `parse_rest_of_item`, `trailer_helper`,
`ambig_ty`, `drop_glue<Expr>` (0.3–0.5 s pipeline each). The pool was
a FIFO queue in declaration order shared by every CGU: a megafunction
lowered late queued behind ~2000 small functions and started when they
had drained, so its half second ran alone.

Critical path for syn, then: frontend 1.4 s → biggest CGU's stage A
(1.2 s) → its lowering (0.36 s) → pool drain tail (~0.8 s).

### kernels-wasm (1 CGU, `--emit obj`)

0.63 s wall (LLVM 0.54). Marks: define 16 ms, iropt 148 ms (serial),
lowering 33 ms, phase B 260 ms, waffle translate+inline+compile+peep
23 ms. Phase B is one function: `hashmap::run`'s pipeline took 250 ms,
158 ms of it `ifconv2`, 59 ms more in the `hmget` closure; samply put
`proots::paramize_r` + `khash_m` at 234 of ~600 codegen samples, under
`clifpeep::webmerge_ctx` (`cparm`/`sameargs`/`webmerge`). `wmprof`
(`PLIRON_TRACE=pliron::clifpeep=info`) showed 8 webmerge rounds of
10–55 ms on that function, 3-slot blocks keying for 3 ms each.

`paramize_r` rewrote a key tree recursively with no per-node memo. A
`Key` is a DAG (`key_of` shares `Rc` subtrees through its memo), so the
walk was tree-sized — exponential in the sharing depth — while
`khash_m` beside it was already address-memoized and therefore cheap.
SipHash-heavy code (hashmap kernels) has exactly those deep shared
operand DAGs.

## Changes

1. **`proots::paramize_r` memo** (`pliron-clif-opt/src/proots.rs`): a
   per-call `FxHashMap<*const Key, Option<Key>>` over inner nodes. The
   result of a node depends only on its content and the call's fixed
   `hmap`/`vmap`/`skip`, so the memoized answer is structurally the
   one the walk rebuilt. Byte-identical: kernels-wasm and regex-wasm
   objects `cmp` equal, syn's 17 rlib object members equal (only
   `lib.rmeta`, which hashes the backend path, differs between two
   dylib paths). No flag: pure speedup.
2. **Largest-first phase-B pool** (`pliron-clif-lower/src/lower.rs`):
   the process-wide fn pool pops the queued job with the most CLIF
   instructions (`dfg.num_insts()` at push, FIFO among equals) instead
   of the oldest. Phase C applies results in declaration order, so pop
   order never reaches the output (determinism R3). `PLIRON_FNLPT=0`
   restores FIFO.

## Left

- syn's stage A (1.2 s serial per CGU for the biggest CGUs) is now the
  critical path: inliner cloning (`clone_blocks_into`, 3.5% of CPU),
  sroa split/forward, nocapture. Parallelizing within a CGU needs a
  shareable `Context`.
- Phase-A lowering is serial per CGU (0.36 s on syn's biggest CGU);
  `FnLower` holds `&mut Module` for declarations, so per-function
  parallel lowering needs the declarations hoisted or batched.
- `webmerge_ctx` on syn is now `web_nf_facts`/`facts_cfg`/
  `canon_map_facts` per round (the per-round Ascent rebuilds PARITY.md
  already names as cross-round-uncacheable).
- `stepcache::pipeline_lookup` (memcache keying) is 1.5% of syn's CPU.
