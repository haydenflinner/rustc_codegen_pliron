## Tried: `PLIRON_INLINE=256` / `384` (IR-level wasm flat limit)

`WASM_LIMIT` is 512. Lowering via `PLIRON_INLINE=N` (overrides small and
native) cut object size and compile wall/RSS:

| N | CODE | ratio | wall | RSS |
|---|---|---|---|---|
| 512 (default) | 401,126 | 1.929× | 3.55 s | 2.06× |
| 384 | 373,045 | 1.794× | 3.16 s | 1.91× |
| 256 | 371,160 | 1.785× | 2.98 s | 1.77× |

Linked `bench/wasm` modules: default 174,920 B → INLINE=384 172,973 B.
Return values of all 16 `k_*` exports match LLVM (iters=3) — not a
miscompile.

**Runtime (`bench/wasm/run.mjs --layouts=3`) rejects the flip:**

| kernel | default | INLINE=384 | Δpp |
|---|---|---|---|
| tokenize | −30.0% | **+42.6%** | +72.6 |
| parse_only | +3.9% | **+24.5%** | +20.6 |
| hashmap | +1.0% | +4.1% | +3.1 |
| geomean | 0.932 | 0.885† | |

†geomean looks better only because `chars_ascii` (−90%) / `fib` (+100%)
hit V8 placement cliffs (byte-identical returns; ranges span the same
cliff). `tokenize` / `parse_only` ranges are tight — real regressions.
Cause: callees in the 384–512 band (e.g. probe/tokenize helpers) stop
inlining under the flat wasm limit; loop-site `hot×` budget at 384 is
1152 and still covers `hash_one` (~926), so hashmap stays near-flat.

Leave `WASM_LIMIT=512`. A wasm-only lower cap is only worth revisiting
with a hot/cold split (keep 512 at loop sites, tighten elsewhere).

## Follow-up: `PLIRON_INLINE_WASM_COLD` (opt-in, default = `limit`)

Hot/cold split in `pliron-ir-opt` small mode: non-loop flat threshold
reads `PLIRON_INLINE_WASM_COLD` (unset → `limit`); loop-site `hot`× still
uses `WASM_LIMIT` so `hash_one` (~926) keeps inlining at 512×3.

| COLD | CODE | ratio | tokenize | parse_only | hashmap |
|---|---|---|---|---|---|
| unset (512) | 394,752 | 1.899× | −30.5% | +3.9% | +1.3% |
| 448 | 393,241 | 1.891× | — | — | — |
| **384** | **360,066** | **1.732×** | **+42.0%** | **+23.7%** | +4.2% |
| 320 | 356,379 | 1.714× | +62.8% | +24.4% | +4.1% |

(`bench/wasm --layouts=3` vs SOLO=50 tip.) Size cliff is 384↔448; the
callees tokenize/parse_only need sit on *cold* sites in that band — the
split preserves hashmap (loop) but not tokenize. Leave unset.

SOLO further below 50 is flat: 40/30/25 only −0.2…−0.8 KiB more.

## `PLIRON_INLINE_WASM_COLDKEEP` (default off, `=1` on)

Left uncommitted in the main checkout on 10-28 with a default-on flip;
committed 2026-10-31 default off. The numbers below were measured at the
SOLO=50 tip and predate the later SOLO/FANIN changes, so re-measure before
flipping.

Name allowlist on the cold cap: non-keep callees see flat 384; keep-list
(hash/num/str/ast-parse/utf8_decode) keeps `WASM_LIMIT`. Applied as the
cold threshold (not a post-hoc reject) so loop sites that miss `hot×`
(`ncalls>2`) still hit the cap.

| policy | CODE | ratio | tokenize | parse_only |
|---|---|---|---|---|
| SOLO=50 tip | 394,752 | 1.899× | −29.7% | +4.1% |
| COLDKEEP | **372,517** | **1.792×** (−22 KiB) | **−30.0%** | +4.9% |
| COLD=384 | 360,066 | 1.732× (−35 KiB) | +42.0% | +23.7% |

Denylist tries (fmt-junk / alloc-math-sort) each *grew* CODE ~1 KiB:
refusing some band members frees caller-cap budget that refills elsewhere,
and fmt specializes when inlined. Allowlist-as-threshold is what lands the
cliff without the tokenize hit.
