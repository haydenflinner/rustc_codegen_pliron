# 2026-10-29: fast inner loop (burst)

Goal: validate a change at ~90% confidence in under 2-3 minutes, with a
sub-30-second tier. Shipped `harness/quick.py` (see `docs/test-harness.md`).
All timings are from a shared 14-core machine at load 8-22, so read them as
upper bounds.

## Why rapier was "100x slower" (696 s vs 4.6 s): it is a cache artifact

`crates.py` wipes `target-pliron` whenever the backend dylib hash changes, but
never wipes `target-stock`. The 4.6 s stock number is a warm no-op build. Cold
vs cold, from the main checkout's logs: rapier stock 3m51 (388 crates), pliron
6m37 (380 crates) = 1.7x; aho-corasick above is 1.0x. The real per-iteration
cost is the forced full rebuild of every dependency through the backend after
each dylib change. `crates.py --deps stock` avoids it for deps (only workspace
members, plus the wrapper path embedding the dylib hash, rebuild). Not measured
on a many-dependency crate (rapier-class) in this burst; expect the win there,
none on tiny crates (aho-corasick: 28 s vs 26 s, test run time dominates).

## What quick.py covers and misses

Covers: compile errors; unit/regression tests of touched passes; verifier
errors, panics and interpreter mismatches of the whole CLIF pipeline over
~15k recorded functions; the stanza regressions for the pass touched; the 19
known-bug fuzz seeds; 24 fresh seeds per run (window advances, so repeated
runs accumulate coverage).

Would NOT have caught, from the history:
- seed 13475 (slot-merge window): the corpus replay checks the interpreter on
  recorded functions with random inputs, and fn11 is not in them; only a fresh
  seed (1 in ~400) or the seed in FUZZ_REGRESS finds it. With the fix in
  FUZZ_REGRESS it is a regression guard now, a discovery tool never.
- NARROWEXT seed 12309 and regex-automata failures: needs the right fuzz seed
  or the crates tier; quick has a 24/400 chance per run per such seed.
- the jumpthread round bug: depends on the shape of a specific function; the
  `jt_*` integration tests are selected for jumpthread edits, which catches
  regressions of known shapes only.
- anything needing the stage-2 build (self-host only failures), runtime perf
  regressions, wasm sysroot (`-Zbuild-std`) failures, cross-CGU interactions
  outside the smoke programs.

## Ideas ranked by time saved (not done)

1. Make crates tier 1 incremental: keep `target-pliron` per-crate and use
   `--deps stock` by default for quick; add `harness/quick.py --crates NAME`
   (rapier-class: 11 min to ~2 min).
2. Stage-2 UI: shard by directory and cache by (test source hash, stage-2
   dylib hash); a rerun after a small backend fix only recompiles tests whose
   object bytes changed (needs per-test object hashing in `selfhost/verify.sh`).
3. Fuzz seed bank ordered by yield plus early exit: `run.py` uses `ex.map`, so a
   failure still waits for all seeds. Switch to `as_completed` + cancel.
4. Cache pliron objects per (source hash, flags, dylib hash) in `run.py smoke`;
   an unchanged object means the run result is unchanged. Gain is small
   because the compile is the cost; only the link+run (<1 s) is saved.
5. Shared `CARGO_TARGET_DIR` across worktrees with per-worktree fingerprint
   dirs is not safe (fingerprints embed absolute paths, so each worktree
   rebuilds anyway; cold build was 208 s here). A `cp -c` (APFS clone) of one
   warm target avoids the cold build for new worktrees only if paths match.
6. Release+debug double rebuild: the debug dylib incremental is 6 s; release
   is only for ctime numbers, so quick never builds it. Not measured here.
7. Disk: shared budget check in quick.py (done: refuses under 15 GB), fuzz
   seed dirs pruned on pass (done; 11.6k dirs had filled the disk).

## fnbisect fast path

`harness/fnbisect.py -- CMD` runs CMD about log2(#fns)+3 times; each run
must recompile, so make CMD a single `rustc` invocation on the reduced
program (a fuzz seed's `p.rs` from `target/harness/fuzz/<seed>/`, kept on
failure), not cargo. Check the minimized set reproduces the original
symptom, then `PLIRON_OPT_FNS=<name> PLIRON_OPT_BISECT=N` for the transform.
