# 2026-11-19: sibling calls, write-only slots, drop-glue floor

Outcome: `PLIRON_SIBCALL` and `PLIRON_DEADSLOT_WRITEONLY` default on;
`PLIRON_INLINE_GLUET` stays opt-in (it trades).

Three knobs from PARITY item 10 (html-rewriter first), picked up from an
uncommitted tree and measured with `harness/placement.py heldout all
--copies 2 --no-cycles` (callgrind exact counts, aarch64-linux-musl;
non-`nop` deltas against the default).

## `PLIRON_SIBCALL` (step `sibcall`, `pliron-clif-opt/src/sibcall.rs`)

`v = call f(..); return v` becomes `return_call f(..)` on aarch64 when
caller and callee share a convention (`SystemV`, `AppleAarch64` or the
internal `tail`), neither signature has a stack argument or a stack
return area (`reg_only`), and no stack slot address can reach the callee
(every use of a slot address, and of the `iadd`/`isub`/`uextend` chains
derived from it, is a load or store address, a compare, or a `nocap` call
operand). Indirect calls convert on `tail` only: the aarch64
`return_call_indirect` pins its target to `x1`, which only `tail` keeps
out of the arguments. lol_html's hot transitions are direct anyway
(`--> #[inline] state` is `return Self::state(self, ctx, input)`); its
indirect ones return to `run_parsing_loop`.

Vendored Cranelift: `SystemV`/`AppleAarch64` accept `return_call` under
the knob (`call_conv.rs`; only the verifier and one `debug_assert` read
it, so no ABI changes), and FASTCC no longer gives up on a function with
a tail call: a direct `return_call` to a callee whose set was recorded
adds that set to the caller's own (`pliron_tail_clobbers`).

html-rewriter's benchmark binary (macOS): `b <function>` tails 276 ->
935 (LLVM 845), `bl; restores; ret` tails 306 -> 110 (LLVM 150).

## `PLIRON_DEADSLOT_WRITEONLY` (`deadslot.rs`)

A slot whose every address use is the address of a plain `notrap` store
loses the stores and then its frame bytes. pulldown-cmark -185k
(-0.37%), html-rewriter -85k (-0.09%), blind-sig +27k (noise), the rest
within a few hundred instructions. In this Cranelift `stack_store` and
`stack_load` are builder helpers that expand to `stack_addr` plus a
store or load, so `stack_addr` really is the only instruction that
names a slot.

## `PLIRON_INLINE_GLUET` (`inline.rs`)

A floor under drop-glue call-site thresholds. As written it ran before
the default-on `PLIRON_INLINE_DROPLIM=64` cap, which took it back: at 90
html-rewriter moved by 40 instructions and the remarks still said
`cost=83 t=64` for `drop_glue<RawVec<u8>>`. It now runs after the cap.

Fixed, at 90 and 100 (non-`nop`):

| program | 90 | 100 |
|---|---|---|
| rust-html-rewriter | -836k (-0.84%) | -786k |
| rust-protobuf | -219k (-0.34%) | -218k |
| pulldown-cmark | -157k (-0.31%) | +263k (+0.52%) |
| rust-json | -70k (-0.14%) | +747k (+1.47%) |
| regex | +172k (+0.35%) | +165k |
| rust-compression | +534k (+1.25%) | +533k |
| blind-sig | +17k (noise) | +22k (noise) |

It trades (compression, regex), so it stays opt-in. Next for it: which
glue `compression` and `regex` lose on (`irdiff.py --env
PLIRON_INLINE_GLUET=90`); a floor limited to glue with one warm call
may keep html-rewriter's gain without them.

## Together, and the flip

`PLIRON_SIBCALL=1 PLIRON_DEADSLOT_WRITEONLY=1` (non-`nop`):
html-rewriter -741k (-0.74%), pulldown-cmark -284k (-0.56%), protobuf
-263k (-0.41%), json -128k (-0.25%), regex -72k (-0.15%), compression
-1.6k, blake3 -10, blind-sig -14k (noise). No program worse: both are
in `DEFAULT_ON`. The vendored Cranelift's `pliron_sibcall()` now reads
"on unless `=0`", like its other default-on knobs.
