# Wasm code size: where regex-syntax's 5.7x comes from

The parity card (2026-10-27-parity-card.md) has the regex-syntax wasm32
object (`--target wasm32-unknown-unknown --emit obj`, one CGU) at 5.68x
LLVM's `CODE` bytes while native is 1.8x. This note attributes the gap and
adds three default-off waffle-inliner flags. Objects built by hand with the
`ctime.py` `regex-wasm` / `kernels-wasm` arguments; sizes are the `CODE`
section (`llvm-size -A`, what `ctime.py` records); per-function sizes from
`wasm-objdump -x`, matched by symbol. Backend at b0e4ada (debug dylib —
code size doesn't depend on the backend's own opt level).

## Flags (all default off, `PLIRON_X=1` to enable)

- `PLIRON_WASM_NOIRRED` — the waffle inliner never splices a callee with
  irreducible control flow, nor into a caller that has it.
- `PLIRON_WASM_NOREC` — the inliner's loop-callsite rule (`PLIRON_WASM_HOT`)
  skips callees in the caller's call-graph SCC.
- `PLIRON_WASM_GC` — after inlining, drop `Local` functions nothing in the
  module references (LLVM's GlobalDCE for the object; the roots and edges
  are those of `pliron-wasm-ld`'s GC, so it only removes what the final
  link would drop).

Diagnostics: `PLIRON_WASM_SIZELOG=1` prints `wsize <waffle insts> <bytes>
<name>` per body; `PLIRON_WASM_INLINE_LOG=1` now also prints `irred <caller>
<- <callee>` when a splice makes a caller irreducible.

## Attribution of the 984 KB gap

| cause | KB | share | how measured |
|---|---|---|---|
| waffle inliner (`winline`), total | 755 | 77% | default − `PLIRON_WASM_INLINE=0` |
| &nbsp;&nbsp;of which: reducifier blow-up on irreducible callees | 376 | 38% | default − NOIRRED |
| &nbsp;&nbsp;of which: loop rule on recursive meshes (drop glue) | ~100 | 10% | NOIRRED − (NOIRRED+NOREC+GC), GC's 17 KB removed |
| &nbsp;&nbsp;of which: remaining loop-rule growth | ~215 | 22% | (GC+NOREC+NOIRRED) − (GC+HOT=0) |
| &nbsp;&nbsp;of which: TINY/SOLO/always rules | ~50 | 5% | HOT=0 − INLINE=0 |
| IR-level inliner | 169 | 17% | `WASM_INLINE=0` − both off |
| codegen vs LLVM with no inlining at all | 60 | 6% | both off − LLVM |
| unreferenced `Local` bodies left in the object | 17 | 2% | default − GC |

Per function (default vs LLVM): 287 shared symbols are 3.30x (620,645 vs
188,022 B); 120 pliron-only symbols hold 570,537 B, two of them —
`Extractor::extract_repetition` (160,862 B) and `extract_concat<Rev<..>>`
(98,490 B), both inlined away by LLVM — are 26% of the whole gap; 53
LLVM-only symbols hold 19,342 B.

### The reducifier blow-up (the biggest single cause)

`PLIRON_WASM_SIZELOG` shows emitted bytes per waffle instruction. Normal
bodies are 6–10 B/inst. In the default object eight bodies were at 20–75
B/inst and held 458 KB of its 1.19 MB: `extract_repetition` compiled 2,174
insts to 160,862 B (74 B/inst), `extract` 1,958 → 110,933, `extract_concat`
1,311 → 98,490.

The cause is waffle's `backend/reducify.rs`: an irreducible CFG is made
reducible by context-sensitive block duplication, which its own header
warns is exponential in loop nesting. Four CLIF-optimized bodies come out
of lowering irreducible (`Seq::cross_reverse`, `escape_into`,
`Extractor::union`, `Seq::optimize_by_preference`; with `PLIRON_OPT_FNS=0..0`
they are reducible, so a CLIF pass creates the side entrance). Alone they
cost 37 KB (20–40 B/inst). The inliner's loop rule then splices
`cross_reverse` into `extract`, `extract_repetition` and `extract_concat`
(the `irred` log shows exactly these four transitions, every one with
"callee irred true"), where the duplication compounds with the callers'
loop nests. `PLIRON_WASM_NOIRRED` refuses those splices: 1,191,906 →
815,735 B. The residual 37 KB is the CLIF pipeline's: `PLIRON_OPT_FNS=~cross_reverse
PLIRON_OPT_BISECT=N` flips `cross_reverse` from 7.9 to 21 B/inst at N=1120,
and unit 1119 (0-based) is `taildup2` — tail duplication creates the loop
side entrance. Making `taildup2` refuse a duplication that would make the
CFG irreducible (only matters for wasm; Cranelift doesn't care natively)
is the follow-up.

### Recursive meshes (`PLIRON_WASM_NOREC`)

With the loop rule, every member of a recursive drop-glue mesh
(`ClassSetItem` → `ClassBracketed` → `ClassSet` → `Vec<ClassSetItem>` →
…) is a loop callsite of another member; each round splices bodies the
previous round already grew, so each member fills `caller_cap` (2,048
insts). `PLIRON_WASM_INLINE_LOG` counted 1,438 splices, 224 of
`drop_glue<ClassSetBinaryOp>` alone. LLVM inlines bottom-up once per site
and never into a recursive cycle. Skipping same-SCC callees for the loop
rule saves ~100 KB here; the mesh members are still 4–15x LLVM's because
the IR-level inliner also unrolls them (`Ast::drop` 19,948 vs 1,275 B).

### Dead bodies (`PLIRON_WASM_GC`)

Only 17 KB at HEAD: `dead_fns` already keeps fully-inlined `Local` bodies
out of the object. (The main checkout's stale `target/release` dylib
emitted 1,651 functions / 2.22 MB for the same input — an older build
without that; don't measure with it.) Still worth having: inlining at the
waffle level frees callees `dead_fns` could not see, and an rlib's members
otherwise carry them to every link.

## kernels-wasm

LLVM 26,827 B. default 62,264 (2.32x); GC 57,397 (2.14x); GC+NOREC+NOIRRED
57,397 (no irreducible or recursive callees here); GC+`HOT=0` 46,182
(1.72x) — the loop rule is what the hashmap kernels' runtime depends on, so
it stays.

## Bench module and runtime

`bench/wasm` built as `run.sh` does (`-Zbuild-std`, std at one CGU, linked
by `pliron-wasm-ld`): LLVM 76,497 B `CODE`; pliron 158,362 B (2.07x) with
and without the three flags — the two modules are byte-identical (`cmp`).
After link-time GC the bench module has no unreferenced locals, no
irreducible bodies and no recursive-mesh loop callsites, so there is no
runtime to measure: the flags change nothing there. They act on the
object/rlib size (and on anything that does have these shapes, such as
regex-syntax).

The flags also have no effect on `kernels-wasm` beyond GC's 5 KB (above).

## Safety and checks

NOIRRED and NOREC only decline inlining decisions; GC removes functions
with no call, `ref.func`, `GOT.func` import, address-taking op or data
relocation, mirroring the linker's GC roots. None of the three changes any
emitted instruction. `harness/gate.py` passed plain (80 jobs) and with all
three flags on, `gate.py --only wasm` (core/std + tests/wasm through the
backend) passed with the flags, and `run.py --suite fuzz --fuzz-seeds
13700:14000` with the flags: 300/300. NOIRRED is a pure size win with no
observed downside and is the candidate to flip on; GC is dead code that
the link would drop anyway.

## What's left

1. Find the CLIF step that makes `cross_reverse` & co. irreducible (37 KB
   here, and a latent exponential for any irreducible hot callee).
2. The IR-level inliner's own growth on wasm (`WASM_LIMIT` 512, hot x3):
   mesh members 4–15x LLVM, `parser::parse` 16,460 vs 760 B.
3. Remaining loop-rule growth (~215 KB): a smaller `caller_cap` for cold
   callers, or LLVM-style bottom-up once-per-site inlining.
4. The irreducible bodies could also be handled in waffle itself: a
   Relooper-style fallback past a duplication budget (its header suggests it).

## Follow-up 1: keep CLIF CFGs reducible (`PLIRON_REDUCIBLE=1`)

The `taildup2` attribution above was wrong by one bisect unit. A direct
check (`PLIRON_CHECK_REDUCIBLE=1`: after every CLIF step, name the step
that first makes a function irreducible) over regex-syntax finds nine
functions turned irreducible, eight by `mergechain` — specifically
`jumpthread::dispatch_dup`, which clones a small pure dispatch block into
a `jump` predecessor — and one (`escape_into`) by `looprot`. With
`PLIRON_DISPATCHDUP=0` only the `looprot` case remains.

Mechanism (both): a block `y` inside loop `L` (its header, in practice)
is copied into a predecessor `p` outside `L`; `p`'s new direct edge into
`L`'s body is a side entrance, and when another edge still enters at the
header the loop has two entries. `looprot`'s case is a header that is a
dispatch, not an exit test: both `brif` arms stay inside the loop, so
after the latch takes the copy the loop is entered at `s1` and at `s2`.

`PLIRON_REDUCIBLE=1` (default off) adds `jumpthread::side_enters` — "would
giving `p` a copy of `y`'s terminator make an edge into a loop `p` is not
in, landing off its header?" over Cranelift's `LoopAnalysis` — and
`dispatch_dup`, `taildup` and `looprot` refuse such clones (`looprot` also
refuses when both arms stay in the loop). With it, `PLIRON_CHECK_REDUCIBLE`
reports zero functions in regex-syntax; `escape_into` compiles 175 insts
to 1,696 B instead of 189 to 4,612. Tests: `pliron-clif-opt/tests/
reducible_dup.rs` (flag on: the outside `jump` pred keeps its jump, CFG
stays reducible) and `reducible_dup_off.rs` (flag off: the same input
turns irreducible — the hazard the first test guards).

| regex-wasm | CODE bytes | ratio |
|---|---|---|
| `PLIRON_REDUCIBLE=1` alone | 824,566 | 3.97 |
| GC + NOREC + NOIRRED | 703,025 | 3.38 |
| GC + NOREC + NOIRRED + REDUCIBLE | **699,200** | **3.36** |
| the four + `PLIRON_WASM_INLINE=0` | 409,068 | 1.97 |

The small step from 703,025 is expected: NOIRRED had already refused to
splice the irreducible callees; REDUCIBLE makes them normal (and so
spliceable again). What it buys is that no function in the object is
irreducible any more, so waffle's duplicating reducifier never runs — the
latent exponential is gone, on native too (Cranelift never cared, but a
`dispatch_dup` into a loop body was duplicating code there as well).
kernels-wasm: 62,264 → 61,697 alone; 56,903 with all four.

Where the remaining 491 KB over LLVM sits, with all four flags on: the
waffle inliner's loop rule 250 KB (`PLIRON_WASM_HOT=0`: 448,870), its
other rules 40 KB, the IR-level inliner 141 KB net (`PLIRON_INLINE=0
PLIRON_WASM_INLINE=0`: 268,167), codegen 60 KB. Turning the IR inliner
off *alone* grows the object to 909,506: the waffle inliner then finds
many more small callees for its own rules. Sample bodies (waffle insts →
bytes; LLVM bytes): `parser::parse` 135 → 1,140 after the IR inliner,
1,930 → 17,521 after the loop rule (LLVM 760); `Ast::drop` 737 → 7,240 and
2,070 → 23,648 (LLVM 1,275); `lift_common_prefix` 915 → 8,038 and 2,238 →
20,631 (LLVM 1,307). Every one of them ends at `caller_cap` (2,048 insts).

## Follow-ups 2 and 3: the loop rule's callees, and recursion at the IR level

Measured on top of the four flags (699,200 B).

**`PLIRON_WASM_HOTLEAF=N` (default off; `1` means 2).** The waffle
inliner's loop rule splices any callee of up to `PLIRON_WASM_HOT` (400)
insts at a callsite inside a loop. Nearly all of what it spliced in
regex-syntax were callees that themselves carry many calls — parser
helpers, drop glue, `Seq` combinators — and each splice exposes those
calls as fresh loop callsites for the next round, so the hot callers all
ran into `caller_cap`. With the rule restricted to callees with at most N
calls of their own (the IR inliner's `PLIRON_INLINE_LOOPCALLS` leaf rule),
the loop rule keeps what it exists for (hashbrown's `hash_one` is a leaf)
and the cascade stops:

| regex-wasm (four flags +) | CODE bytes | ratio |
|---|---|---|
| — | 699,200 | 3.36 |
| `PLIRON_WASM_HOTCAP=1024` (loop-rule budget per caller) | 625,657 | 3.01 |
| `PLIRON_WASM_HOTCAP=512` | 548,378 | 2.64 |
| `PLIRON_WASM_HOTLEAF=4` | 478,033 | 2.30 |
| `PLIRON_WASM_HOTLEAF=1` (≤ 2 calls) | **451,110** | **2.17** |
| `PLIRON_WASM_HOT=0` (rule off) | 448,870 | 2.16 |

kernels-wasm: 56,903 → 46,787 with HOTLEAF=1 (LLVM 26,827; rule off
46,182). `PLIRON_WASM_HOTCAP` is the budget alternative; it keeps more
and saves less, so HOTLEAF is the one to flip. `parser::parse`: 1,930 →
442 insts (4,490 B; LLVM 760), `Ast::drop` 2,070 → 746 (7,291 B).

**`PLIRON_INLINE_SMALLSCC=1` (default off, small mode only).** The IR
inliner's flat 512-op wasm limit lets every member of a recursive
drop-glue mesh take one full level of the mesh (`PLIRON_INLINE_SCC` stops
only the second level). With no inlining along a call-graph cycle (callee
in the caller's SCC, or self-recursive), `Ast::drop` is 140 insts /
1,370 B (LLVM 1,275), `lift_common_prefix` 3,811 B (from 8,038),
`parser::parse` 3,225 (from 4,490); the module only shrinks 451,110 →
447,128 because the mesh members now stay out of line as separate bodies.
It is the right shape, not a big number. Of the existing knobs,
`PLIRON_INLINE=256` (LLVM's threshold is 225) takes the module to 417,597
on top of HOTLEAF; a flip of the small-mode limit is a bench question.

Where the remaining ~240 KB over LLVM sits now: 268,167 B with no
inlining at all vs LLVM's 207,914 with its inlining (codegen), the IR
inliner's net +140 KB, the waffle inliner's other rules +40 KB.

Flip of `HOTLEAF` (and the related size flags) waits on a nightly job that re-measures regex-wasm size and kernels-wasm runtime; the default gate keeps these off and only runs the fast legs (`wasm_smoke`, unit, stanzas).
