# Spills, part 2: slotprom's sync traffic and lifetimes

Follow-up to 2026-10-27-spills, whose top leftover was `PLIRON_SLOTPROM`
(CLIF stack-slot promotion, on by default) costing several KB on
regex-syntax, then the regalloc2 redundancy it ranked second. Three
default-off flags:

| flag | where | what |
|---|---|---|
| `PLIRON_SLOTPROM_SYNCCOST=1` | `pliron-clif-opt/src/slotprom.rs`, `pipeline.rs` (`s_slotprom`) | a slot whose bounded-call syncs cost more than promotion removes stays in memory |
| `PLIRON_SLOTPROM_LT=1` | `slotprom.rs` (`kills_of`, `run_lt`), `slotmerge.rs` (`marker_whole`, `marker_slots_lt`), `lower.rs` | a promoted field's value ends at its slot's lifetime markers |
| `PLIRON_RA2_XBLOCK=1` | `vendor/regalloc2/src/ion/moves.rs` | the redundant-move eliminator keeps its state into a call's return block |

## Cause 1: sync writebacks outweigh the promotion (`SLOTPROM_SYNCCOST`)

`Ast::fmt` inlines the heap visitor. Its stack is a slot of two `Vec`
headers (six i64 fields) whose address only reaches `&mut` (nocapture)
calls: `push`, `pop`, grow. slotprom promotes such a slot and syncs it:
every promoted field of the slot is stored before each bounded call and
reloaded after it (the sync set is conservative: all fields, every call).
With ~20 bounded calls, the function went from 76 loads + 23 stores
before slotprom to 155 + 58 after, and the six fields became block params
on almost every block of the visitor loop. The same holds for the other
losers (`extract_repetition`, `lift_common_prefix`, `notate`).

Fix: per slot, compare the sync cost (fields x (writeback + reload) at
each bounded call) with the benefit (the field loads and stores
promotion removes), both weighted by a block-frequency estimate (8x per
loop level, to 512x; /8 in cold blocks). The slot stays in memory when
the cost is not lower. Slots with no bounded call are unaffected, so
call-free hot loops promote as before; a cold `reserve_rehash` inside a
hot loop is cheap at weight 1 against accesses at weight 8.

## Cause 2: promoted fields have no lifetime bounds (`SLOTPROM_LT`)

The same pattern as `PLIRON_LTUNDEF`, one level down: a slot field
promoted to SSA carries its last value through every path, around loops
and into sync writebacks, even where the slot is dead. Lowering already
records each `llvm.lifetime.{start,end}` marker as (slots, anchor inst,
block). Under the flag, `kills_of` turns the markers whose position is
still exact (one slot, anchor inst still in the marker's block, or no
anchor and the block still in the layout) into kills. A kill is a
"store of undefined": liveness stops there, so no block param carries a
dead value, and reads after it see the field's undef value. Lost or
moved anchors are dropped, which only leaves a range longer.

A marker on part of a slot (its pointer is a field address, or its size
is smaller than the slot) must not kill the whole slot. Lowering now
records the marker's constant size, and under the flag
`marker_slots_lt` records a partial marker with its slot listed twice,
which every consumer (slotmerge, slotprom) treats as ambiguous.

Soundness relies on what stack coloring (slotmerge) already relies on:
no pass moves an access of a slot across its markers. One more hazard is
shared with slotmerge: tailmerge merges identical blocks without looking
at markers, so a marker in one copy applies to paths through the other.

Alone, LT saves 800 B; with SYNCCOST, 64 B more. Most of its effect was
in the sync-heavy slots that SYNCCOST now leaves in memory.

## Tests

- Unit tests in `slotprom.rs`: a kill at a loop body's top drops the
  header param (2 params without it, 1 with it); a kill after an anchor
  keeps the earlier load and forgets the value for the later one;
  `kills_of` keeps only exact singleton markers; `marker_whole` needs
  the slot base and a full size; the sync cost keeps an adjacent
  store/call/load in memory and promotes a hot loop field with a cold
  bounded call.
- `tests/slotprom_lt` (stanza `slotpromlt`): per-iteration locals filled
  through `&mut` calls and an `Ast::fmt`-shaped heap-stack visitor; the
  output must match under no flag, LT, and both (it matches stock rustc
  too), and `walk`'s spill bytes must drop under SYNCCOST (128 → 88; a
  dylib without the change fails).

## Cause 3: redundant-move state dies at call returns (`RA2_XBLOCK`)

On the "both" object, regalloc2 stored a reloaded, unchanged value back
to its own spill slot 36 times (single-register forms, 11 functions).
Nine are in one place in `push_class_open`: nine values are reloaded
into callee-saved registers before a cold call and stored back after it.
regalloc2's redundant-move eliminator would elide such a store (it
tracks which allocation holds a copy of which), but it clears its state
at every block boundary, and a `try_call` ends its block: the store-back
sits in the return block.

Fix: under the flag the state survives into a block whose only
predecessor is the block right before it in instruction order. The
instructions in between (the call included) still clear what they define
or clobber, as within a block. Store-backs drop from 36 to 2. The flag
removes more than those: other moves whose destination already holds the
value, for -2,208 B alone and -2,272 B on top of the slotprom flags.
regex-syntax and both test programs pass the regalloc2 checker
(`PLIRON_RA_CHECK=1`) with it. The duplicate `br_table` edge reloads
(5-9 blocks) are not addressed.

## Not done: the parser leftovers

- `pop_group`, `pop_class` and `parse_with_comments` have 323, 202 and
  303 spill accesses (408/368/264 B of spill slots). The cause is
  aggregates moved by value through calls in a loop: `concat =
  self.push_group(concat)?` copies the 72-byte `Concat` into an argument
  temp, the call writes a `Result<Concat>` through sret, and the payload
  is copied back. SROA splits every temp of that chain into 8-byte
  scalars, so the value is live as nine SSA values across the loop and
  its calls: each arm reloads nine spills, stores them into the argument
  temp, calls, loads the result and spills nine again. `pop_group` does
  the same with the 224-byte `GroupState` popped off the stack. LLVM
  keeps such values in memory and copies with `q` registers.

  Two experiments (not committed): keeping copy-only allocas of at least
  64 B in memory made `parse_with_comments` 416 B smaller but the crate
  2,048 B larger (`Hir::concat` +960); keeping them only when a call lies
  between the copy-in and a copy-out was still +1,344 B. Without
  forwarding, each link of the copy chain becomes a real memcpy. A fix
  needs memcpy-chain forwarding into one home slot (call-slot forwarding
  of the sret result into the loop-carried local) before the SROA
  decision, and SROA leaving that home slot in memory.

## Next steps, ranked

1. The memcpy-chain home-slot work above (several KB on the parser).
2. One reload per `br_table` edge instead of one at the join (5-9 blocks).
3. Sync only the fields a bounded call can reach (the callee's operand
   extent), not every field of the slot. That lets SYNCCOST keep more
   slots promoted.
