# Spills: dead locals around loops, and constants pinned across calls

Follow-up to 2026-10-27-code-size, where spill reloads were the largest
single item in pliron's 2x code size on regex-syntax. Two causes, two
default-off flags:

| flag | where | what |
|---|---|---|
| `PLIRON_LTUNDEF=1` | `pliron-ir-opt/src/sroa.rs`, `pliron-clif-lower/src/lower.rs` | a lifetime marker on an SROA-promoted local redefines its variables as zero |
| `PLIRON_REMATCALL=1` | vendored Cranelift `egraph/elaborate.rs`, `opts/remat.isle` | one-instruction `iconst`s rematerialize, also into loops that contain a call |

## Cause 1: promoted locals carried around loops (`PLIRON_LTUNDEF`)

`NestLimiter::check` inlines `HeapVisitor::visit`, a loop with calls. Its
CLIF going into regalloc (`PLIRON_PRECOMPILE=1`) had a loop header with 60
block params, 45 of them pass-through webs: 15- and 16-word copies of
`Result<(), ast::Error>` locals, initialized to 0 at entry, carried
unchanged through every block, with one real use each (a `select` or a
`store` on the error-return path). The function's 624 B of spill slots were
mostly these, nine accesses each.

Origin: rustc's `Ok(())` for that type writes only the niche word. SROA
splits the 128-byte local into 16 slices, which lowering turns into
Cranelift variables. On the `Ok` path the other 15 slices keep "whatever
was there", which in SSA is last iteration's value. So the payload of an
`Err` from iteration *i* flows around the backedge into iteration *i+1*.
No read can observe it: the local's `llvm.lifetime.start`/`end` bracket
each iteration, and the contents are undefined outside them. But SROA
dropped the markers for the slices (they stayed on the parent alloca,
which lowering ignores once promoted).

Fix: `split` clones the parent's markers onto each promoted slice
(`inherit_markers`, which already did this for escape copies). Lowering
turns a marker on a promoted alloca into `def_var(var, 0)` for each of its
variables, so the old value's live range ends at the marker. Two details
mattered:

- The zero is emitted at the marker but excluded from later markers'
  anchors (`FnLower::ltzero`). Anchored on a zero that then dies, a
  real-slot marker falls back to its whole block, and slotmerge stopped
  sharing NestLimiter's 56-byte error-kind temps (slots 280 → 560 B). A
  per-type zero hoisted to the entry block instead avoided that but cost
  more than it saved: one constant live across the whole function
  (`visit_post` spills 128 → 296 B).
- `forward_single_store` skips marker uses under the flag (they touch no
  bytes); otherwise the new markers would block single-store forwarding of
  the slices. Forwarding past a `lifetime.start` is sound: the load would
  read undefined bytes, which the stored value refines.

Soundness relies on what stack coloring already relies on: no pass moves
a read of a local past its `lifetime.end` or before its `lifetime.start`.
memcpyopt's call-slot forwarding treats a marker on the destination as a
touch and bails.

## Cause 2: constants pinned across calls (`PLIRON_REMATCALL`)

Classifying spill slots by what is stored into them (a script over the
disassembly: a slot whose every store writes a register just set by
`mov #imm`; single-register `ldr`/`str` only, so a lower bound), the
pre-COLDCOPY object reloaded constants from spill slots 1,319 times and
frame addresses 222 times; with COLDCOPY 778 and 216, and with both flags
45 and 80. In `lift_common_prefix`, `0` is
reloaded 90 times and the element size `48` 27 times. In `pop_group`, `0`,
`1` and `-1` sit in spill slots.

The egraph places a constant once above the loop, and two PLIRON rules
keep it there: `iconst` is not marked for remat at all (remat.isle), and
`maybe_remat_arg` never clones into a deeper loop or into another block of
the def's loop. Both were for hot call-free loops (a radix constant
re-materialized per digit block). Regalloc2 has no rematerialization, so
in a loop with calls the constant takes a callee-saved register or a spill
slot.

Fix: under the flag, one-instruction `iconst`s (`imm64_remat_cheap`) are
remat values again, and both loop rules give way when the use block's
innermost loop contains a call (`Elaborator::call_loops`, one pass over
the blocks, marking each call block's loop and its parents). The flag also
reaches `stack_addr`, which was already a remat value but was held by the
same loop rules. Call-free loops keep the old placement.

## Tests

`tests/spills` (stanza `spills`): a NestLimiter-shaped visitor with an
inlined inner loop, per-iteration `Result<(), Error>` locals collected on
`Err`, and an aggregate carried across iterations. It builds with neither
flag, `LTUNDEF`, and both, and diffs the output (which also matches stock
rustc). It also requires `ltu_visit`'s spill bytes to drop under
`REMATCALL` (80 → 24); a dylib without the change fails that check.
The program does not reproduce the 45-param web itself, so the
LTUNDEF leg is a correctness check only. Before the rebase,
the gate passed with `PLIRON_LTUNDEF=1` set for every job (apart from the
`spills` leg, run against a dylib that predated the REMATCALL change).
With neither flag, the regex-syntax object was byte-identical to the
commit before the change.

## Left

1. `PLIRON_SLOTPROM` (CLIF slot promotion, on by default) costs 5.8-8 KB
   here (measured before COLDCOPY): `=0` gives 401,872 → 394,288 alone,
   396,240 → 388,240 with LTUNDEF, and 384,624 → 378,864 with both flags
   (spill loads 5,576 → 4,946). It exists for hot-loop speed (hmget, quicksort), so turning it
   off is not the answer. The biggest losers are `extract_repetition` (+1,888 B) and `Ast::fmt`
   (+1,056 B). It is the same pattern as cause 1, one level down: slot
   fields promoted across loops and calls without lifetime bounds.
   slotprom could use the `lifetimes` lowering already records.
2. Redundant re-spills: regalloc2 reloads a value and stores it back to
   the same slot unchanged (`ldr x2,[sp,#0x368]; ...; str x2,[sp,#0x368]`;
   about 60 single-register cases, more in pairs), and puts one reload
   per `br_table` edge block instead of one at the join.
3. `pop_group`, `pop_class` and `parse_with_comments` barely moved (spills
   336-416 B). Neither cause dominates them. Not yet diagnosed.
4. The `umulh` magic constant for exact division by 48 holds a
   callee-saved register (or four `movk`s if rematerialized). This is the
   division work's exact-`sdiv` lever.
