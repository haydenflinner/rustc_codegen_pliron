# Optimizing only the code that runs (2026-11-22)

Question: how much compile time does the backend spend on code the
benchmark never executes, and what does skipping it cost at runtime?

Setup: the hot list for each held-out program is every function with a
nonzero callgrind count in its run (`PLIRON_OPT_FNS=@list`, exact mangled
names; aarch64-unknown-linux-musl builds as `bench/heldout/irdiff.py` makes
them, so the names match the profile). Clean builds of the whole crate
graph, `RUSTC_WRAPPER=` (`~/.cargo/config.toml` sets sccache, and the
held-out sources live outside this repo's no-wrapper config), 14 cores,
load average about 11. `none` is `PLIRON_OPT_FNS=0..0`: no function
optimized, the floor of the backend's optimization cost.

Executed code: html-rewriter 389 of 1,881 functions (95 hold 99% of the
instructions), pulldown-cmark 214 of 1,183 (43), regex 487 of 1,854 (49).

| program | config | wall | CPU (user+sys) | runtime instructions |
|---|---|---|---|---|
| html-rewriter | LLVM | 8.0 s | 22.7 s | 85.83M |
| | pliron full | 7.8 s | 27.9 s | 93.58M |
| | pliron hot only | 7.4 s | 19.1 s | 96.54M (+3.2%) |
| | pliron none | 6.6 s | 15.0 s | 216.88M |
| pulldown-cmark | LLVM | 2.6 s | 5.2 s | 45.33M |
| | pliron full | 2.8 s | 8.2 s | 46.70M |
| | pliron hot only | 2.8 s | 6.1 s | 47.36M (+1.4%) |
| | pliron none | 1.2 s | 2.6 s | 181.76M |
| regex | LLVM | 3.3 s | 13.5 s | 45.97M |
| | pliron full | 4.0 s | 22.2 s | 46.78M |
| | pliron hot only | 2.9 s | 11.8 s | 47.08M (+0.6%) |
| | pliron none | 2.2 s | 5.4 s | 152.11M |

Readings:

* Hot-only cuts build CPU by 26-47% (below LLVM's CPU on html and regex)
  for +0.6..3.2% runtime instructions. Wall time barely moves: the critical
  path is the frontend and lowering of the one big crate, and proc-macro
  crates (`syn`), which optimization does not touch.
* The ceiling of this lever is the `none` row: no optimization at all is
  1.9x (html), 3.2x (pulldown), 4.1x (regex) less CPU than a full build.
  A 10x compile-time factor is not in skipping optimization; it is in not
  recompiling what did not change (incremental reuse of per-function
  results) and in the serial MIR -> pliron front half.
* Not explained yet: hot-only should cost nothing at runtime when every
  executed function is optimized; html's +3.2% says interprocedural inputs
  (inlined callee bodies, IPO summaries, xcgu copies) still depend on
  unselected functions being optimized.

A real tiering needs a hot set without running the program (static
frequency estimate, or a PGO profile when there is one).
