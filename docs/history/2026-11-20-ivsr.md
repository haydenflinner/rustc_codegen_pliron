# 2026-11-20: loop strength reduction onto a pointer IV (`ivsr`), SLOTCOMB cap

## The gap

`rust-compression`'s hottest line after SLOTCOMB is brotli `hq.rs:517`
(`EvaluateNode` inlined into `BrotliCreateHqZopfliBackwardReferences`):
`nodes[pos + 1]` with 20-byte nodes. Ours per trip:
`add x0, x20, #1; ldr x1, [sp, #9512]; madd x6, x0, x17, x1; ldur w0, [x6]`
(base spilled, reloaded every trip). LLVM: `add x8, x19, x25`, a pointer IV.
Neither `lsr` (rebases onto an existing pointer IV) nor `ivptr` (index-rebuilt
pointer params) creates a new one.

## `ivsr` (`PLIRON_IVSR=1`, opt-in)

New header parameter `p = base + S*i + k0` per `(i, base, S)`; entry edges
compute it, back edges pass `p + S*c`, addresses become `p + (k - k0)`.

Rules found by measuring (each one a loss without it):

- **Address already carried.** lol_html's selector VM passes
  `base + 120*(i + 1)` back to the header: replacing it gave a second
  register for the same pointer (weighted static +5.3k). Values passed on
  the back edge are skipped, as are loops with a parameter stepping by `S*c`.
- **Every trip.** A group needs an address in a block dominating each latch.
- **Not innermost-only.** `SplitByteVector` (1040-byte histograms, an
  inner loop per trip) is a static loss, but restricting to innermost loops
  drops the per-position loop, which contains inlined inner loops.
- **Loop size does not separate wins from losses.** `UpdateNodes`' win is a
  19-instruction loop; html's losing attribute loops are 6 and 18. The
  floor stays a knob (`PLIRON_IVSR_MIN`, default 0).

aarch64's `madd` makes `base + i*S` one instruction, so `ivsr` only pays
where the base or the stride were under register pressure. Without a
pressure estimate at CLIF level this stays opt-in.

## `bump_hoist` and the IV (`PLIRON_BUMPHOIST_INLOOP=1`, opt-in)

With `ivsr` the header read `ldr w0, [x4], #20` and two arms paid
`sub x0, x4, #20`: phase 2 of vendored Cranelift's `bump_hoist` rewrites every
other use of the base as `q - k` so the post-index fires, assuming those uses
leave the loop. `INLOOP` skips a base read again in a block every trip runs.
Alone it loses: pulldown-cmark +0.22% (+109k executed jumps: the bump kept in
the latch keeps that block), compression +0.13%.

## SLOTCOMB

Cap at two terms (a third piece costs a shift and an OR against one store:
regex +0.06% before). Single-read slots only (blake3 +3k loads before).
Committed `92b450c6`; no program worse, ready to flip after gate and crates.

## Afternoon: decide after allocation (`PLIRON_IVSR=2`)

No CLIF-level rule separated the winners from the losers, so the backend
now decides per function after register allocation: apply `ivsr` to a copy
of the optimized function, compile both, and keep the copy when its
frequency-weighted code is smaller. The cost is a new hook in vendored
Cranelift's emitter: each block's bytes / 4 times its placement frequency,
regalloc's moves, spills and reloads included (`pliron_cost_take`). Two
scratch compiles happen only where `ivsr` changes something.

Static frequencies do not know trip counts. lol_html's attribute map-fold
(one to three trips) looked 2.7% cheaper with the rewrite and lost (+14k
executed: a callee save and the entry multiply per call), while brotli's
loop looked 0.5% cheaper and won 1.2%. The cost is therefore split: the
copy must also not grow the code that runs at most once per call (blocks
with frequency at most the entry's). That rejects the map-fold and keeps
brotli's `BrotliCreateHqZopfliBackwardReferences` and `UpdateNodes`.

`INLOOP` became a count. pulldown-cmark's byte cursor is read once more, by
its end test, and its latch is `add; b`: fusing costs one `sub` and empties
the latch, so the old "skip if read every trip" rule paid a jump per byte
(+109k). Now a base is skipped only when it has more every-trip use blocks
than an emptied latch saves.

`LocalNameHash::update` keeps one top exit test and every `match` arm ends
`mov; b top`. `looprot` now copies the test into up to `k` latches. The
microbench goes 164.8M -> 146.1M (LLVM 147.0M).

|---|---|---|---|---|---|---|---|
| none | -0.032% | -0.082% | +0.301% | +0.493% | -0.578% | -0.059% | -0.015% |
| header values stay in header | +0.129% | +0.048% | +0.092% | **-0.399%** | **-0.426%** | -0.058% | -0.016% |

Compression's first loss was `is_mostly_utf8` (+240k): its header also adds

## Split budget (`PLIRON_RA2_MAXSPLITS`)

The regex loss under `LOOPROT_MULTI` came from regalloc2. aho-corasick's end
bound arrives in `x3`, a call at the entry clobbers `x3`, and the value had
already used upstream's two splits on its loops: the third request fell back
to minimal bundles. The hot latch's reload then hinged on which register a
temporary took. With a budget of 4 the loop keeps the bound and the
automaton pointer in registers, with or without the rotation.

## Partial inlining of entry guards (`PLIRON_PARTINLINE`)

html's state functions exist on both sides, so they compare cleanly:
`finish_tag_name` 1.39M (LLVM) vs 2.36M, `tag_name_state` 1.09M vs 1.73M,
`tag_open_state` 0.54M vs 0.96M, `data_state` 1.03M vs 1.41M (callgrind
per-address counts against the disassembly). `finish_tag_name` runs 66
instructions per call for LLVM, 112 for us. The largest single difference:
every call (21,082) calls `drop_glue::<TreeBuilderFeedback>`, which the
inliner refused (cost 151 > 64: the `Box<dyn FnMut>` variant's drop is
inlined into it), for a variant that owns nothing. The call also stops the
`Option` result just stored on the stack from forwarding to the test after
it. LLVM inlines and folds it.

The new IR pass copies such a callee's entry guard in front of each call.
Three things kept it from firing at first: it ran after `xcgu-home` (the
drop glue is a cross-CGU copy that becomes an import there), calls carry
an unused result even when void, and cargo hides rustc's plain stderr
(trace by running the crate's `rustc` command from `cargo build -vv`).
Without a branch expectation layout put the skip out of line (+32k
jumps); with it:

## `rangefold` over pure trees (`PLIRON_RANGEFOLD_TREE`, opt-in)

`tag_name_state`'s letter test `b'a'..=b'z' | b'A'..=b'Z'` stayed two range
checks: each arm passes its own copy of `(c & 31) + 5` to the join, two
levels deep, and `rangefold` only re-emitted one pure inst and compared
args one level deep. With trees of three levels it folds both pairs and
merges them into `(c | 32) - 97 u< 26`. Re-emitting the tree in front of
the test made it run on every byte; a landing block on the hit edge fixes
that statically, but html stays +0.052% either way: `tag_name_state` gains
12k and `tag_open_state` loses 63k, three register copies per call (the
input slice moved to other registers and back) and the hash step hoisted
back in front of the test by a later pass. Opt-in.

## Threading a storing merge (`PLIRON_MERGETHREAD`, 2026-11-21)

The register copies in the tag-scanner state functions (`mov x9, x2` ...
`mov x2, x9` around every byte) sit around one shape: `consume_ch` returns
`Option<u8>` and bumps the stored position on both paths, so the merge of
`Some(ch)`/`None` holds `pos + 1; store` before `brif flag`. Each edge passes
a constant flag, but `jumpthread` threads pure merges only and `taildup`'s
escape repair could not order the use-blocks (and refused stores). The new
step copies such a merge into each incoming edge when the successors each
keep a single predecessor, renaming the uses under each successor to its
copy's values; no SSA repair is needed. `tag_open_state` 103 -> 88
instructions.

## Copies of by-value params (`PLIRON_MEMCPYOPT_SRCFWD`, opt-in)

The 152 -> 144 chain above starts at a by-value param: rustc passes
`ExecutionCtx` by pointer, the callee owns the bytes (`noalias`), MIR moves
it into a local and `stack_item` out of that local. LLVM reads such a
temporary from the param (memcpy-memcpy forwarding, then GVN). New rule in
memcpyopt (`run_srcfwd`): a temporary whose only writers are whole copies
from `param + off` and whose uses are loads, copy sources, markers and drop
glue reads the param, unless a write to the param can run between a copy
and a read (one forward walk from the copies, one from the writes they
reach; a call that may keep the param's address makes every non-local write
count). It runs after phisimp (an inlined callee's by-value param reaches
it through block arguments before that) and again after the xfacts adopt.

Exact counts (2 copies): html -0.354% (`LimitedVec<StackItem>::push`: the
item param copied to a temp and the temp into the vector, -134k there and
-134k in `memcpy`; the three bailout paths' 152-byte temps), compression
-0.174% (`Vec<ZopfliNode>::extend_with`), protobuf +0.003% (only in
`memcmp`, `free` and a `RandomState` map: per-run hashing), the rest within
noise. The test `srcfwd` fails with the clobber check disabled.

Not taken: `exec_without_attrs`'s own 144-byte copy. `ctx` reaches
`add_execution_branch(&mut self)`, whose body passes it on to
`RawVec::grow_one` (another CGU, unknown even after the adopt with
`PLIRON_NOCAP3=1`) and stores a pointer derived from it for hashbrown's
`reserve_rehash`; with the address possibly kept, `LimitedVec::push` and
drop glue between the copy and the reads may write it. Cross-CGU nocapture
for `grow_one` is the next lever there.

`PLIRON_MEMCPYOPT_SRCFWD` flipped (`DEFAULT_ON`, `=0` off) after the gate
and crates tier 1 with dependencies through the backend (20 crates, no
pliron-only failure).

## foldhash's sponge across joins (`PLIRON_WIDE128_PHI`)

The rest of `add_execution_branch`'s per-call gap: foldhash builds a
`u128` sponge (`sponge |= x << sponge_len`, flushed at 128 bits), so each
`Hash` write is a shift by a constant 0 or 64 that LLVM folds. Ours ran
the generic 128-bit variable shift (`lsl/lsr/orr/tst/csel`), shift amounts
reloaded from the stack. Two blockers: the function (654 insts) is over
`wide128`'s 512-inst cap, and the sponge crosses the flush/no-flush joins
as an `i128` block param, a use `wide128` does not fold.

| cap 700 / 800 | 0 / -0.160% | -0.264% / +12.7% |
| split every param, mul-free folds over the cap | -0.194% | +12.7% |
| foldable params only, mul-free folds over the cap | -0.060% | +13.0% |
| foldable params only, over the cap only where one split | -0.060% | +0.089% |

`montgomery` (between 700 and 800 insts) cascades whenever the folds run
on it, multiplies or not; the last row skips it because none of its
params (128-bit adds) qualifies. Committed with the gate and crates not
run (user's call). Iffy, logged: blind-sig's +0.089% is mostly allocator
and RNG noise, but `montgomery` itself is +8.4k (0.02%) against html's
-58k. The params the gate excludes (a loop with a variable `sponge_len`)
were worth another -0.13% on html when split.

`PLIRON_WIDE128_PHI_ALL` (default on): every eligible `i128` param split,
over the size cap only in functions with at least one foldable param.
Against the foldable-only split: html -0.107%, blind-sig -0.099% (inside
its 40k spread), the rest flat. Validation skipped (gate/crates not run).

## One seed address per block (`PLIRON_CSE_SYM=2`) and `guardsink`

hashbrown's `reserve_rehash` for `SelectorHandlersLocator` (75 against 152
instructions per call, 6.5k calls, zero items on that path) loaded
foldhash's seed address (non-colocated, a GOT load) five times in one
block: copies from the inlined hash calls that `licm` hoisted side by
side, which nothing merged. `PLIRON_CSE_SYM=1` (opt-in since earlier)
merged them, also across dominator scopes: html -0.149%, pulldown +0.051%
(`parse_block` spills the one long-lived copy). `=2`, block scope only:
html -0.149%, every other program flat. Default `=2`; gate and crates
not run.

The same values sat above `looprot`'s zero-trip guard (licm's preheader
became the guard). `guardsink` (opt-in) moves such values past the
`brif` into the loop side: html -0.046% alone (and with `=2` html
-0.121%, worse than `=2` alone), compression +1.62%, pulldown +0.55%,
protobuf +0.09%, mostly extra loads in each program's hottest function.
Kept opt-in, not understood.

## Tail-call arguments and the state functions (`PLIRON_TAILARGCOPY`)

`TagScanner::tag_name_state` (1.09M LLVM, 1.73M ours): the per-byte loop
ran 9 instructions against 3, four of them `mov`s rotating the input
pointer and length through scratch registers, plus a second load of the
byte. The input is a plain function parameter in the CLIF; the loop's
exits call a helper with it in `x2`/`x3` and `return_call` the next state
with it in `x1`/`x2`. Calls already copy multi-use arguments
(`arg_detach`); tail calls did not, so the input's bundle held both fixed
requirements, regalloc2 split it at the tail call inside the loop
("requirement conflict"), and the pieces moved every byte. Detaching
tail-call arguments too: html -0.396%, protobuf -0.144%, json +0.007%,
blind-sig +0.020%, the rest within noise. Default on; gate and crates not
run.

## Sparse equality chains as search trees (`PLIRON_EQTREE`)

A class count of every executed instruction (callgrind, both binaries)
put constant materialization first in html's gap: 6.51M against 4.31M.
`TreeBuilderSimulator::get_feedback_for_start_tag` tested the tag's
`LocalName` hash against a dozen constants in a chain (`matches!(tag,
A | B | ..)`), each constant two or three `mov`/`movk`; LLVM's
SimplifyCFG makes the chain a switch and lowers it as a binary search
(`b.gt`/`b.le` on midpoints). `eqtree` does the same for chains of six or
more distinct constants on one value: html -0.384%, blind-sig +0.082%
(RNG and allocator functions: noise), the rest flat. Default on; gate and
crates not run.

Other classes of the gap, same count: register copies +1.27M, stack
stores +0.81M, memory loads +0.81M, executed alignment `nop`s +0.43M
(LLVM 11).

## Copies of a by-value push (`PLIRON_XCGU_LEAF_DEPTH=12`)

html with `-Ccodegen-units=1` runs 1.049x LLVM's time against 1.091x
(instructions 1.085x against 1.101x): cross-unit inlining is worth about
1.5% of instructions. A bigger plain copy limit is not the way:
`PLIRON_XCGU_SIZE=150` gave pulldown -1.47% but json +2.90% and html
+0.10%. lol_html's `LimitedVec::push` (95 MIR statements, 10.4k calls from
another CGU, each with a 144-byte `memcpy` of the item) fit the leaf limit
of 100, but the leaf walk stopped at depth 8: `push` -> `push_mut` -> the
item's drop glue on the unwind path -> `LocalName` -> `BytesCow` -> `Cow`
-> `Vec` -> `RawVec` -> `RawVec::drop` -> `deallocate`. At depth 12 (same
numbers as 14): html -0.094%, pulldown -0.057%, blind-sig -0.06% (noise),
protobuf +0.037% (prost's `merge_repeated` takes in `merge`, +67k; logged
as an accepted trade), the rest flat. Also tried: `#[inline(never)]`
callees as leaves (no further gain), and the `cold_path` intrinsic needing
no body (`PLIRON_XCGU_COLDPATH=1`: copies of a push in the other CGUs
too; html +0.12% because `Element::get_attribute` absorbed ~0.85M and
stopped being inlined, json +1.08% together with the deeper walk).
Default on; gate and crates not run.

## Constants across calls (`PLIRON_EXNCONST`, measured, opt-in)

lol_html's `exec_without_attrs` loops over selector jumps calling a
matcher through a vtable; the loop held the constants 0, 1 and 1 in
`x21`/`x24`/`x27` and reloaded `self` from the stack on every trip. One of
them was a drop flag passed on each `try_call`'s exception edge (edgefwd
had removed the forwarding pad), which made it live across every call.
`exnconst` gives each such edge a cold landing block that defines the
constant: `self` stays in `x28`. Exact counts: html -0.10%, json -0.065%,
compression +0.30% (brotli's `BrotliCreateHqZopfliBackwardReferences`
spills a loop bound it kept in `x23` before: 120k reloads), pulldown
+0.044%. Only constants with no other use (`_DEAD`, removed): html +0.03%,
the rest noise. The two remaining constants are the late GVN's shared
`iconst 0`/`iconst 1`: a step giving every using block its own copy
outside call-free loops (`cremat`, removed) lost html +0.17%, pulldown
+0.39%, blind-sig +0.36%, compression +0.53% (`pop_up_to` and
`escape_double_quotes_only` paid a `mov` per trip for a register they had
free). Which constant to hold in a register across calls is a register
pressure question for regalloc, not for a CLIF step.

## `with_capacity` + extend (`PLIRON_SELARGS_EXT`)

lol_html lowercases every tag and attribute name with
`str::to_ascii_lowercase`: `Vec::with_capacity(len)` then a `map` collect.
Names average 4.4 bytes, so LLVM's 64- and 8-byte vector loops never run
and both sides use a scalar loop of the same length per byte; the
difference is per call (115 against 92 instructions). Part of it: after
`__rust_alloc` we built `cap = ptr == 0 ? 1 : len` and the pointer as two
`csel`s and then branched on the same test, and the extend's `len > cap`
grow test stayed. `selargs` resolves such selects on branch edges, but the
branch tested `uextend` of the compare until the late egraph stripped it,
after `selargs` ran. Looking through the extension, then threading the
edge whose arguments decide the grow test (`edge_selfcmp`): json -0.165%,
html -0.056%, blind-sig -0.041%, the rest flat. The first version also
threaded past blocks whose params later blocks read (regalloc2 panicked on
an entry live-in in serde_json); fixed with filetest `selargs_ext_dom`.
Default on; gate and crates not run.

## Small copies in small functions (`PLIRON_MEMFAST_SMALLFN=1024`)

lol_html writes its output through `&mut dyn FnMut(&[u8])`: one closure,
`Vec::extend_from_slice`, out of line on both sides (LLVM folds the two
identical closures of `token_produced` and `text_token_produced` into one
symbol). 62.8k calls of a few bytes, each a libc `memcpy`: 24 instructions
a call for LLVM, 33 for us before the copy itself. Runtime-size copies
below 16 bytes are inline only on CFG cycles without a profile
(`MEMFAST_SMALL=loop`); a function small enough to stay out of line and
still be called is the same case. Exact non-nop, threshold 64 / 256 /
1024 / every copy (`MEMFAST_SMALL=1`): html -0.27 / -0.27 / -0.29 /
-0.29%, json 0 / -0.12 / -0.41 / -1.99%, protobuf 0 / 0 / -0.83 / -0.85%,
pulldown 0 / -0.01 / -0.18 / -0.19%, the rest flat. .text at 256 / 1024 /
every copy: regex +0.37 / +1.44 / +2.17%, html +0.25 / +0.59 / +1.41%,
compression +0.19 / +0.46 / +1.01%, pulldown +0.24 / +0.46 / +0.52%, json
+0.03 / +0.25 / +0.43%, protobuf 0 / +0.04 / +0.04%. Default 1024. json's
remaining 1.6% is in `serialize_str`, `format_escaped_str_contents` and
`visit_str`, bigger functions; gate and crates not run.

## memchr's NEON mask (`PLIRON_BITCAST2`, `PAIRWISE_ISLE`, `MINMAXIMM`)

The lexer's state functions (`tag_name_state`, `data_state`, ...) are
8.38M instructions against LLVM's 6.07M. `data_state` is memchr: per call
LLVM narrows the 16-byte compare mask with one `shrn`, we used `ushr;
movi; and; sqxtun`, and the 64-byte loop's `vpmaxq_u8` test was `uzp1;
uzp2; umax` against one `umaxp`. The vendored aarch64 backend already had
a `shrn` rule for the `extractlane` of that narrow; the frontend's
`vtrunc` ends in `bitcast.i8x8` and memchr's `vreinterpret_u64_u8` casts
straight back to `i64`, and the inner cast took the `sqxtun` rule first.
Folding bitcast round trips (`PLIRON_BITCAST2`), pairwise rules
(`PLIRON_PAIRWISE_ISLE`) and the untimed `PLIRON_MINMAXIMM` (`smax x, 0`
as `cmp x, #0; csel x, x, xzr`): exact non-nop html -0.312%, pulldown
-0.338% (each alone: -0.193/-0.214%, -0.017/+0.010%, -0.085/+0.012%; the
pulldown losses are spills in `scan_code_fence`), json +0.079% (one
alignment `nop` in `parse_str` became a callee-saved store and load, same
instruction total), the rest flat. Default on; gate and crates not run.

## Switches as bit tests (`PLIRON_BRBITS`, measured, opt-in)

`tag_name_state` switches on `b - 9` through a 54-entry `br_table` with
three non-default destinations; LLVM tests the byte against a 64-bit mask
(`lsr; tbnz`). `brbits` does the same, but the mask came back into the loop:
the pipeline's licm hoisted it, and the final egraph's elaboration placed
it at its use again (`ELABKEEP` keeps a hoist only for instructions with an
operand the loop does not use, which a constant never has). Keeping wide
constants hoisted (`PLIRON_ELABKEEP_WIDE`) costs pulldown +0.45% (its own
masks then spill), and with both on html is +0.34% (the lexer's switches
reach their special bytes often enough that the chain of tests costs more
than the table), pulldown +0.52%, regex -0.12%. Both stay opt-in.

## Jump-table clamp (`PLIRON_JT_DIRECT`)

Cranelift's aarch64 jump table follows its bounds branch with `csel idx,
xzr, idx, hs`, zeroing the index under misspeculation (a sandbox
mitigation), and the narrow-table load then reads through the copy. LLVM
emits neither for native code. Indexing the table with the index register
directly: pulldown -0.342%, protobuf -0.138%, html -0.093%, json -0.039%,
the rest flat. Default on; gate and crates not run.
