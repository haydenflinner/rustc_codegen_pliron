# Crate-wide capture summaries (`PLIRON_NOCAPSUM`, opt-in) — 2026-11-23

## Why

html's `SelectorMatchingVm::exec_without_attrs` copies a 144-byte struct
onto the stack and reads fields back from the copy, where LLVM reads them
from the source (`selectors_vm/stack.rs:196-197`, about 0.5-0.7% of html's
samples). memcpyopt's `srcfwd` refuses: the source "may be captured".
`PLIRON_TRACE=pliron::memcpyopt=debug` now names the use that decided it
(891a9a69): `ExecutionCtx::add_execution_branch`. Its `self` reaches
`RawVec::grow_one`, then `RawVecInner::finish_grow`, and also hashbrown's
`reserve_rehash`, each in another CGU. xfacts adopts only facts each CGU
solved on its own, so a chain of cross-CGU hops never resolves.

## What

- `nocapture` (under `PLIRON_NOCAPSUM=1`) also runs a summary form of
  its Datalog program (`CapSumProg`). A call to a callee with no body
  in the CGU is not a capture but an edge
  `dep(f, i, callee, k)`. Edges are followed through the bodied
  callees, so each param ends as `Captured` or as the set of bodiless
  callee params it reaches.
- Summaries are published with the CGU's other facts. Copies merge per
  param: captured in any copy means captured, and edges union.
- Behind rustc's thin-local LTO barrier (`PLIRON_XFACTS_ALL=1`), the
  first `facts_adopt_all` solves every summary once (`solve_capsum`).
  The solve is a least fixpoint of captured (copy, param) pairs over the
  edges. An edge to a symbol no CGU summarized under that type captures.
  Bodiless declarations take the solved set, and `nocap3` reruns with it
  (then `srcfwd2`).

Unit tests: `nocapture::capsum_tests` (a three-hop chain, imports and
cycles, the merge).

## Result: no win, kept opt-in

The solve resolves the cross-CGU hops, but `add_execution_branch` still
captures its `self` for two local reasons:

1. A pointer derived from `self` (the hash builder inside hashbrown's
   `make_hasher` closure) is stored into a stack slot, and the slot goes to
   `reserve_rehash`. A store of a derived pointer counts as a capture
   unless the slot never leaves the function. Freeing it needs
   "pointee" capture facts: what a callee does with pointers stored in
   the memory it is given. LLVM's `captures(none)` does not model that
   either.
2. A block param joins a `self`-derived pointer with others and flows into
   the indirect `match_handler(..)` call (flow imprecision).

macOS retired instructions, one `ab.py` run each, 7 rounds, against the
defaults:

| program | `XFACTS_ALL` | + `NOCAPSUM` |
|---|---|---|
| html | +1.3% | +0.9% |
| regex | +0.1% | +0.8% |
| compression | +0.1% | +0.2% |
| json | +0.0% | +0.1% |

A 3-round pass over all eight changed the code of seven of them. Its
regex -1.4% was noise: the default build read 65.11M in one run and
63.58M in the next. Compare sides within one `ab.py` run only.

## Next, if this is taken up again

Pointee-capture facts for closure environments (1), and a field- or
path-sensitive join for block params (2). Without both, the crate-wide
solve has nothing to unlock on the eight programs.
