# 2026-11-16: licm hoists loads that run on every loop entry (N6)

PARITY N6: under single-caller inlining (`PLIRON_INLINE_ONCE=1` or `=3`)
hmget's lookup loop kept the map-header loads, because `&HashMap` is read
out of the closure environment and carries no `dereferenceable` fact,
and licm required one for every load hoist.

## The rule (`PLIRON_LICM_GTE=1`, opt-in)

`licm::guaranteed_loads`: start at the header, follow the straight line
of blocks a plain `jump` leads to inside the loop (never back to the
header), collect `notrap` loads, and stop at the first call, return,
trapping instruction other than a `notrap` memory access, or conditional
terminator. Such a load may hoist to the entry edge without a
dereferenceability proof.

Why it is sound:

- The hoisted load sits on the loop's entry edge: before `pinst` when
  that is a plain `jump h`, otherwise in a block split onto the edge. It
  runs only when the header runs next, so it never runs on a path that
  skips the loop (a zero-trip guard stays above it).
- On that first iteration the original load runs with the same address
  (licm already requires loop-invariant operands), and nothing ahead of
  it can stop the iteration (no branch, call, return or trap) or call
  out (no call can free or map memory in between). The program makes
  the access anyway; hoisting moves it earlier within the same entry.
- The value is not covered by this argument: the existing clobber scan
  still requires that no loop write reaches the location.
- Linear: one walk per loop, at most 64 blocks, no CFG rebuild.

Tests: `pliron-clif-opt/tests/licm_gte.rs` (header and jump-chain loads
hoist onto the entry edge and not above a zero-trip guard; loads behind
a branch, after a call, after a trapping `udiv`, or with a clobbering
store stay; the two hoisting tests fail with the knob off).

## Effect

Corpus replays with `--check` (no status change anywhere):

| corpus | knob | functions changed | instructions |
|---|---|---|---|
| std (native, 4,925) | GTE | 2 | +15 |
| wasm-dsa-eval every 4th (17,369) | GTE | 47 | +276 / -20 |
| wasm-dsa-eval every 4th | NOPRESS_WASM | 57 | +1,185 / -367 |
| wasm-bench (2,662) | GTE | 2 | +18 |
| wasm-bench | NOPRESS_WASM | 8 | +159 / -23 |

Wasm kernel module, function by function (`wasm-objdump -d`):

- default build: GTE changes nothing (byte-identical module); NOPRESS
  changes only `core::num::flt2dec::strategy::dragon::mul_pow10`.
- ONCE=1+NCC+SLOTPROV, ONCE=3+SLOTPROV: GTE changes only `k_hmget`;
  NOPRESS gives the same `k_hmget` and also changes hashbrown's
  `reserve_rehash` and `mul_pow10`.
- ONCE=1 or ONCE=3 without SLOTPROV: GTE changes nothing (the SipHash
  tail-buffer store to a stack slot clobbers; SLOTPROV clears it).

hmget against LLVM (`node bench/wasm/run.mjs ... --layouts=3 hmget`, load
46-62, machine shared; the timing script waited for load under 10 and
never got it):

| build | knobs off | + GTE | + NOPRESS_WASM |
|---|---|---|---|
| default | +5.5% | same module | +5.5% |
| ONCE=1 | +19.0% | same module | +18.8% |
| ONCE=1 + NCC + SLOTPROV | +10.7% | = NOPRESS code | +1.1% |
| ONCE=3 | +19.1% | same module | (GTE+NP) +19.4% |
| ONCE=3 + SLOTPROV | +11.5% | +2.2% | +1.9% |

The coordinator's quieter window (load under 10) gave the same order:
default +5.7%, ONCE=1+NCC+SLOTPROV +10.5%, the same plus
`PLIRON_LICM_INNERPRESS=0` +1.1%.

## Ready to flip?

GTE changes no wasm kernel in the default build and only `k_hmget`
under single-caller inlining, so no other wasm kernel can lose to it.
Native: two std functions change (+15 instructions); the native kernels
and held-out programs were not measured, so the flip should be on wasm
first (or after a held-out A/B), together with SLOTPROV (and NCC for
ONCE=1), which hmget needs as well. NOPRESS_WASM is not needed once GTE
is on and touches more code: leave it opt-in.
