# Code size: where pliron's 2x on regex-syntax goes

The parity card's new SIZ input (machine-code bytes, `harness/ctime.py`)
put pliron at about 2x LLVM. regex-syntax at `-O -Ccodegen-units=1
--emit=obj`, new defaults (2026-10-27-defaults):

| | functions | `__text` bytes |
|---|---|---|
| LLVM | 401 | 184,752 |
| pliron | 399 | 401,872 |
| shared by both, LLVM | 336 | 170,728 |
| shared by both, pliron | 336 | 324,592 (1.90x) |

The 63 pliron-only functions (77 KB) are mostly bodies LLVM inlined
everywhere or never instantiated (`hir::visitor::visit` for the printer,
`StrSearcher::next_match`, `HirKind::eq`). The 1.9x on functions both
emit is the main gap.

## By instruction class

Whole object, instructions (objdump), extra = pliron - LLVM:

| class | LLVM | pliron | extra |
|---|---|---|---|
| `[sp]` loads | 3,420 | 16,537 | 13,117 |
| ALU (incl. inline jump tables) | 7,477 | 20,112 | 12,635 |
| branches | 7,422 | 13,985 | 6,563 |
| `[sp]` stores | 2,934 | 9,051 | 6,117 |
| moves | 7,950 | 13,644 | 5,694 |
| compare/select | 4,309 | 7,684 | 3,375 |
| other loads | 5,053 | 7,360 | 2,307 |
| other stores | 3,412 | 4,982 | 1,570 |
| calls | 3,238 | 4,621 | 1,383 |
| total | 46,188 | 99,444 | 53,256 |

- **Stack traffic, 36% of the gap.** Splitting `[sp, #off]` accesses by
  Cranelift's frame layout (outgoing args, then explicit slots, then
  spill slots; sizes from `PLIRON_FRAME_INFO=_R`): 9,327 spill loads and
  3,896 spill stores, against 5,788 slot loads and 3,776 slot stores.
  Spill reloads alone are the largest single item. `NestLimiter::check`
  has 624 B of spill slots, against LLVM's whole 416-B frame, and 468
  stack loads against 56. LLVM also copies with 16-byte `q` registers
  where pliron uses 8-byte pairs.
- **Jump tables in `__text`, about 16 KB.** objdump decodes them after
  `br xN` as ~4,000 `udf #imm`s. Cranelift puts them inline at 4 B per
  entry. LLVM puts them in `__const`, compressed to 1–2 B.
- **Branches: 3,800 extra unconditional `b`s**, which points at block
  layout and jump threading.
- **1,416 extra `umulh`**, fed by a register holding a magic constant
  and leading into size arithmetic. Likely division of a pointer
  difference by a non-power-of-2 element size, which LLVM knows is exact
  (`sdiv exact` becomes a multiply by the modular inverse). Unverified.
- Calls are only 1.4x, so inlining is not the main driver. The bodies are
  larger per operation.

## Levers, by size

1. Spills: the register pressure in large match-heavy functions
   (`NestLimiter::check`, `Translator::visit_post`). Also on the open
   list for stack (2026-10-26-inline-recursion).
2. ALU and moves: per-op lowering quality, not yet split further.
3. Jump tables out of `__text` with narrow entries (Cranelift emission).
4. Exact division for slice lengths, once confirmed.

Scripts (scratchpad, not checked in): per-function sizes from `nm -n`
address deltas, the instruction-class split, and the `[sp]` offset split
against `PLIRON_FRAME_INFO`.
