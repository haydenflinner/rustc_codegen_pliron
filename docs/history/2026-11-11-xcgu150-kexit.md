# 2026-11-11 — XCGU_SIZE=150 ICE fix, punroll KEXIT A/B, decompress census

## jumpthread stale-base ICE (aaec1ed)

`PLIRON_XCGU_SIZE=150` crashed `opt cgu.N` on pulldown-cmark:
`dfg.rs:325 index out of bounds: len 38248, index 4294967295`
(`u32::MAX` = `Value::reserved_value()`).

Bisect (`fnbisect` over the cmark build, then `PLIRON_TRACE=pliron::step`
span closes) showed the panic inside `jumpthread::NonNull::is_deps_at`
via `is_m_at` ← `fold_null_tests` ← `s_jtround`. The culprit functions
were the 6 callers that had received an xcgu copy of
`scalar_iterate_special_bytes`.

Root cause: `NonNull::site_derived` resolved recorded
`site_facts.derived` bases with `resolve_aliases`. A recorded base whose
alias chain ends at the reserved slot (the base's def was deleted/merged
by an earlier step) panicked. Fix: `try_resolve_aliases` + skip stale
sites; `RegionNN::holds`'s `derived` walk hardened the same way — a
tombstoned base makes the fact unusable, not the query unanswerable.
Same convention `derived_base` already used for tombstones.

Not xcgu-specific — any stale site/derived base could hit it; size-150
copies just made it likely. Gate 94/94, fuzz 399/399; all 8 held-out
benches build at XCGU_SIZE=150 after the fix.

## punroll KEXIT (8b80588, opt-in)

`montgomery` (blind-sig) grew 4 loops 8x each — decrementing/store and
swap loops keeping a data-dependent exit per copy (`icmp`+`brif` each).
The latch test amortizes; the kept exits don't. `run_loop`'s
`unroll_width` is body-size only — no kept-exit term (peel path has
`16/exits`, counted path had nothing).

New opt-in `PLIRON_PUNROLL_KEXIT=N`: `k = min(k, N/(kept+1))`.

- KEXIT=8 (k≤4 @1 exit): geomean 1.002 — compression 0.971*,
  json 1.022*, blind-sig 0.996.
- KEXIT=4 (k≤2 @1 exit): geomean 1.000 — blind-sig 0.937, protobuf
  0.982*, but regex 1.069*, json 1.046*.

Kept exits aren't uniformly bad — some loops complete their copies
profitably. Left opt-in, same status as `PUNROLL_FNMAX`.
