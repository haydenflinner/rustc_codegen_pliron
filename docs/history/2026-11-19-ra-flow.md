# 2026-11-19: register moves as a labelling / flow problem (design note)

## The measurement that motivates it

`docs/regalloc.md` "Move kinds": on the 2026-11-18 night builds, edge
moves (copies at block boundaries, where a value sits in different
registers on the two sides of an edge) are the largest excess kind on
six of eight held-out programs. Compression executes 1.11M of them
against LLVM's 0.04M, 35% of its whole instruction gap; regex 18%,
pulldown-cmark and protobuf 11%, html-rewriter 9%. `callarg` (copies
into argument registers before a call) is second: html-rewriter +0.73M,
pulldown +0.36M, json +0.25M. Moves are not most of the gap anywhere
except compression (overhead as a whole is 8-43% of it, 2026-11-18
table), but they are its cheapest part to attack: no inlining or
codegen change, the allocation alone.

## The framing

One value's register, block by block, is a labelling problem (a Potts
model): sites are the blocks where it is live, labels the registers
plus memory; a unary cost per (block, label): infinite where another
value holds that register, a preference where a fixed register follows
(x0 before a call that takes the value first); a pairwise cost per CFG
edge whose ends disagree: a move or a spill/reload, weighted by the
edge's frequency. Minimizing it is "keep this value still". Graph cuts
solve it: α-expansion (Boykov, Veksler, Zabih) is a sequence of binary
min-cuts, each "switch these blocks to register α or keep their label",
exact when the other values are held fixed.

What already exists in the vendored regalloc2: `PLIRON_RA2_REGION`, an
exact min-cut per candidate register over a bundle's blocks (one binary
step of the above, used for splitting), and `PLIRON_RA2_REHOME`, the
greedy one-site version (a join-only block takes the cheaper side of its
edges).

The general form is a multi-commodity flow: each register a track
through program time, values routed along tracks, a track switch a move,
the memory track a spill, rematerialization a source edge (Koes and
Goldstein). It models moves, spills, remat and instruction-specific
register preferences in one cost, which ion's bundle heuristics do not.

## Koes and Goldstein's progressive allocator: what became of it

"A global progressive register allocator", PLDI 2006, and David Koes's
CMU thesis "Towards a More Principled Compiler: Register Allocation and
Instruction Selection Revisited" (CMU-CS-09-157, 2009). A
multi-commodity network flow model, two fast heuristic allocators on it,
and a progressive solver (Lagrangian relaxation) that improves the
allocation the longer it runs: on average 3.47% better than GCC's
allocator with little time, 6.84% with more (code size, x86-32). The
companion "Register Allocation Deconstructed" (SCOPES 2009) used the
optimal model to measure which parts of allocation matter.

No production compiler picked it up that we found. Our reading of why:
the gains were measured on x86-32 (eight registers, irregular) and in
code size, so they looked smaller on 16-32-register targets; the
progressive mode costs compile time a production compiler rarely grants;
and LLVM's greedy allocator (2011) took the most profitable piece cheaply
(region splitting placed by `SpillPlacement`, an approximate min-cut).
The model-based family did reach LLVM as PBQP (`-regalloc=pbqp`, Scholz
and Eckstein), used for irregular targets.

Why it can pay here anyway: the excess we measure is exactly what the
model prices (moves on edges), our targets are not register-starved so
the flow problem is mostly unconstrained, and the expensive part can be
spent only where a profile or loop depth says the edges are hot.

## Plan

1. **Basic form, post-allocation** (opt-in `PLIRON_RA2_POTTS`): after
   ion, for each value with executed edge moves (loop-weighted), try
   α-expansion over the registers free in its live blocks, everything
   else held fixed; keep the relabelling when the weighted move count
   falls. First version: one expansion round per value, one register
   per value (the trivial labelling: a register free over the whole
   range) before the general cut. Checked by `PLIRON_RA_CHECK` and
   rafuzz, measured by `rastat.py dyn` move kinds and `placement.py`.
2. **Unary costs from instruction selection**: fixed-register uses
   (call arguments, returns) as preferences in the same energy, and
   commutative operand order chosen by it (`callarg`).
3. **Portfolio**: several allocations per hot function (ion, MCTS,
   greedy, the relabelled one, randomized expansion orders), the one
   with the lowest weighted static cost kept. Budgeted by size and loop
   depth.
4. **Oracle**: exact dynamic programming over the series-parallel / loop
   structure of small hot functions (structured programs have small tree
   width, Thorup 1998), to measure how far each allocator is from the
   optimum.

## Results (2026-11-19, the basic form)

`PLIRON_RA2_POTTS` (`vendor/regalloc2/src/ion/potts.rs`): per value, in
order of current edge cost, up to 8 candidate registers, two rounds of
α-expansion, each a Dinic min-cut on the value's through-blocks; kept
when the exact energy falls by more than 1/16. Checker-clean on 50,000
rafuzz seeds and on std and clcg (`PLIRON_RA_CHECK=1`); a unit test
compares the cut with brute force on 2,000 random energies.

Static, std corpus, loop-weighted (`rastat.py static`): mode 2 (trust
frequencies) moves -3.9%, overhead -2.2%, weighted instructions -0.6%;
mode 1 (Pareto) moves -0.9%, overhead -0.45%.

Exact executed instructions (non-`nop`, `placement.py heldout all
--copies 2`):

| program | `=2` frequencies | `=1` Pareto |
|---|---|---|
| blind-sig | -112k (-0.33%) | -63k (-0.18%) |
| pulldown-cmark | -137k (-0.27%) | -2k (noise) |
| rust-html-rewriter | -119k (-0.12%) | -96k (-0.10%) |
| rust-protobuf | -64k (-0.10%) | -49k (-0.08%) |
| rust-compression | -18k | -2k |
| rust-json | -15k | -1k |
| blake3-scalar | -6k | -6k |
| regex | **+203k (+0.41%)** | -8k |

The regex loss is one function, `Fsm::follow_epsilons`: the static model
gives each arm of the eight-way `EmptyLook` dispatch the switch's full
share (each arm ends in a branch back into the loop, which placement
calls likely), so mode 2 traded eight reloads in arms that are cold in
practice for reloads on the inner back edge and the loop entry, +220k
loads. Static weights cannot see that, so mode 1 only takes steps that
give no edge of the value a new move: a gain under every profile.
Mode 2 is for profiled builds (`PLIRON_PGO_USE`), not yet measured there.

Compression keeps its edge moves under both modes: they are not an
allocation choice. In `brotli::enc::utf8_util::is_mostly_utf8` the loop
increments are computed before a conditional branch whose other path
still reads the old counter (`add x11, x7, #1; add x9, x10, #1; cbnz;`
then on the split back edge `mov x7, x11; mov x10, x9`); LLVM computes
them on the back edge itself. The fix is placement: sink a pure value
whose only uses are the branch arguments of one edge into that edge.
Next candidate after this.

**Flip (2026-11-20):** `=1` default on. Gate green, `crates.py --tier 1
--deps pliron` 20 crates with no pliron-only failure, std corpus codegen
time unchanged (10.4 s either way).

## Round 2 (2026-11-20): copies and the latch fold

Two causes the move-kind table pointed at, each opt-in, then measured
alone and together (non-`nop` exact counts):

| program | `POTTS_COPY=1` | `LATCHSPEC_LIVE=1` | both |
|---|---|---|---|
| pulldown-cmark | -0.41% | -0.36% | -0.78% |
| rust-compression | 0 | -0.56% | -0.57% |
| rust-protobuf | -0.20% | -0.01% | -0.22% |
| rust-html-rewriter | -0.12% | -0.01% | -0.13% |
| regex | -0.07% | -0.02% | -0.09% |
| rust-json | -0.02% | noise | -0.02% |
| blind-sig | noise | -0.07% | noise |
| blake3-scalar | 0 | noise | 0 |

`PLIRON_RA2_POTTS_COPY`: call arguments go through `arg_detach` copies
when their CLIF value has other uses; when lowering then folds those uses
away (stores into `sp`-relative addressing), the copy is the source's
only use, but ion allocates the long source before the tiny copy and its
copy hint never sees the destination's `x0`. After allocation both are
known: a single-range source takes the copy's register when free, and the
copy is dropped at emission. Pareto over every copy of the range, so it
cannot lose; checker-clean on std, clcg and rafuzz (the fuzz `Func` now
reports every one-use one-def instruction as a copy: 520 relabelled
copies in 20,000 seeds under each mode).

`PLIRON_LATCHSPEC_LIVE`: the compression placement problem was
`latchspec` folding a latch into the branch before it while the other
successor still read the old counter. A first version (any use outside
the blocks dominating the branch) refused folds that cost nothing and
lost on four programs (blind-sig +0.10%, jumps +47k); the second asks
the real question, reachability of a use from the other successor
without passing the header, and loses nowhere.

What is left of the `callarg` moves after these: a value that could
land in its argument register only if the last use of that register's
occupant came first (`ldp x5, x2, [x1]; add x3, x1, #56; ... mov x1, x5`):
instruction order and allocation decided together.

**Flip (2026-11-20):** `POTTS_COPY` and `LATCHSPEC_LIVE` default on.
Gate green, `crates.py --tier 1 --deps pliron` 20 crates clean. (The
first gate run failed on the latchspec test's control half, which called
`run()` and so picked up the new default; it now passes the rule
explicitly.)

## Round 3 (2026-11-20): pieces

`PLIRON_RA2_POTTS_PIECES`: the Potts nodes of a value include its partial
block pieces (live in and dying in the block; defined there and leaving
or dying) and its register copies inside them are pairs (other side
fixed), so the copy preference and the edge moves are one α-expansion.
Two follow-ups before the flip:

- A piece that ends inside its block where ion split the value now pairs
  with the value's next range. Without it a Pareto step could add the
  move at the split; with it the energy also pulls the piece toward its
  neighbour (std static moves -3.1% -> -4.3%, callarg -0.8% -> -4.2%).
- No relabel brings a callee-saved register into a block that has none:
  with `PLIRON_SHRINKWRAP=1` the pass had put the early-return test's
  second load into `x19` ahead of the branch (saving a move, costing the
  save on the early path; `tests/shrinkwrap.rs` caught it in the gate).
  Statically free (moves -4.35% vs -4.32%).

## What the remaining call-argument moves are (2026-11-20, static, std)

After `POTTS_COPY`, the std corpus still has 185k weighted `callarg`
moves. Classified by the latest definition of the copied register in the
same straight line: 64% have none there (the value comes from an earlier
block: mostly a long-lived value held in a callee-saved register across
calls and copied into the argument register at each, which LLVM does as
well), 11% computed, 9% constants, 8% loads, 6% stack addresses, 1%
symbols. Rematerializing the constant/address/symbol 16% would swap a
move for a recompute (same instruction count) and only relieve register
pressure. So the `callarg` excess against LLVM on the held-out programs
is mostly not an allocation choice; differences in inlining and call
counts are the likelier cause. Not pursued further.

Two edge-move shapes that are also not allocation choices, for the
record: `miniz_oxide::inflate::core::init_tree` passes a loop-invariant
value as a header parameter on every in-loop edge and another value on
three others, so the parameter and the invariant interfere in the header
(regalloc2 rightly refuses the merge) and each edge pays a move;
regex's `Fsm::next_state` copies a cursor start that stays live
(`x25 <- x26`) into its inner loop.
