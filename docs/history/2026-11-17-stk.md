## driftsort_main: not FRAGCOPY

The 11-13 card blamed `frag_copy_stays_whole` (`PLIRON_SROA_FRAGCOPY`).
With `PLIRON_SROA_FRAGCOPY=0` both `driftsort_main` monomorphs still had
8272 B frames. `PLIRON_TRACE=pliron::memcpyopt=debug` names the refusal:
`tmp could promote; dst escapes to a call`. `AlignedStorage::<T,
4096>::new()` is now inlined, so the scratch is a `memset` into a 4 KiB
temp copied whole into the slot `drift::sort` receives. The 11-11
promotion guard (`2e60688f`) protects a temp written only by non-call
ops, because sroa might still promote it. A temp over sroa's `MAX_SIZE`
(512 B) never promotes, and `BIGTMP` no longer protects it. Both frames:
8272 -> 4160 B (LLVM 4176). Stanza `bigtmp`.

## What FRAGCOPY does cost

`PLIRON_SROA_FRAGCOPY=0` took STK 1.097 -> 1.034 (on top of BIGTMP).
Two effects:

1. Aggregates that stores build and one copy moves out
   (`Box::new(PropertiesI { .. })`, 80 B; `Parser::new`). Whole, they
   are a stack slot plus a copy; split, the copy becomes the stores
   into the destination. `PLIRON_SROA_FRAGCOPY_OUT=<min bytes>` lets
   those split:
   - `=1` (any size, any coverage): regex +0.36% (`Fsm::next_state`),
     pulldown +0.05%, compression +0.10%.
   - `=32`: regex +0.19%, all in `CompileClass::c_utf8_seq`. A 32-byte
     enum with 14 bytes nothing writes still pays the split copy a store
     per piece. Fixed by requiring a store on every piece except less
     than a word of padding (`PropertiesI`'s last byte).
   - `=32` with the coverage rule: pulldown +0.09%. 32-48 B `Item`s
     pushed into a `Vec` keep their pieces live across the grow call.
   - `=64` with the coverage rule: none worse; STK 1.076 -> 1.043, the
     same frame win as `=32`.
2. `visit_class_set_item_post`: 1600 B with FRAGCOPY, 880 without. The
   final CLIF differs in a few instructions (one 32-byte slot more), but
   regalloc2's spill area is 1200 B against 512. That is spill-slot
   assignment in regalloc2 (other agents' area); not touched here.

## Stale lifetime markers (KILLSLIDE)

`Parser::parse_with_comments` had seven 128-byte `Result` sret slots,
one per match arm, none shared (`PLIRON_SM_INFO=all
PLIRON_SM_INFO_FN=..`: `stale markers on 8 slots`). In each arm `slp`
pairs two `i64` loads of the result into one `i64x2` load, placed at the
stores it feeds. That is after the end marker, which is anchored on the
last scalar load. The stale check then drops every marker of the slot.
Without markers the sret call (which reads before it writes) makes the
slot live across the whole parser loop, so all eight overlap.
`PLIRON_SM_KILLSLIDE` moves an end kill past reads of its slot that
follow it in the same block, up to the first write or start of that
slot. A later kill only lengthens the range, and the stale check still
runs on the moved kill. 1712 -> 816 B (LLVM 992). Stale slots in
regex-syntax: 20 -> 8; the rest have reads in later blocks. Test
`pliron-clif-opt/tests/slotmerge_killslide.rs`.

## Checks

- xcorpus (pass off against on), std and wasm: no mismatch for
  `BIGTMP` and for `FRAGCOPY_OUT=1`, whose splits include `=64`'s.
- `clif-check report --check` under `PLIRON_VERIFY=full` with
  `KILLSLIDE`: std 4244 ok / 681 inconclusive (same as without), wasm
  2080 / 391.
- The gate's poison stanzas with `KILLSLIDE` + `BIGTMP`: all pass.
  `harness/gate.py` on the flipped tree (`bdef917c`): 121 jobs passed.
- Native kernels: only `k_hmget` changes with `KILLSLIDE` (a 48-byte
  copy before the loop goes); `k_iterw` and `k_tokenize` change with
  `FRAGCOPY_OUT=64`. The machine ran at load ~160, so these were judged
  by retired instructions and cycles at `-benchtime 20x` (`/usr/bin/time
  -l`): equal within run-to-run noise (<= 0.1%). Not timed on a quiet
  machine.
- wasm kernel module: byte-identical with all three (159,493 B).
