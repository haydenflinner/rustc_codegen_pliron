## Landed

### `PLIRON_LINDIS` (default on): `a[i]` survives a store to `a[i + 1]`

`loadfwd::lin_form` reads an address as `base + scale * idx + k` (an
`iadd` of `ishl`/`imul` of an `iadd`-constant chain, or scale 1); two
with one base, index and scale differ by exactly their `k`s modulo 2^64,
so a store keeps the locations whose bytes it cannot reach. `root()` saw
`base + ((i + 1) << 2)` and `base + (i << 2)` as unrelated pointers.
brotli's literal-cost prefix sums (`ZopfliCostModel::set_from_literal_costs`,
`literal_costs[i + 1] = literal_costs[i] + carry`) reloaded `a[i]` after
every store in the unrolled body: float loads in the function 47 -> 34.
rust-compression -0.5..-0.7% instructions, cycles -2.5..-6%; the other
seven binaries byte-identical; std corpus 4 functions smaller. Locations
reach a point only when available on every path in, so a location keyed
by an in-loop address never survives the loop header and the index form
compares one iteration's values. Test `loadfwd_lindis`.

Left: the loop-carried half (LLVM's LoopLoadElimination). The unrolled
body still loads `a[i]` once per trip, the previous trip's last store;
forwarding it needs a header parameter and an entry value through the
peeled prologue's join. Off the fadd dependency chain, so small.

### `PLIRON_RA2_RELOADCOPY` (default on): reload into the copy's destination

regalloc2 post-allocation (`ion/postopt.rs::reload_into_copy`): an edit
filling `r` just before a register copy `mov d, r`, where nothing reads
`r` before it is written again in the block, fills `d` instead and the
copy becomes `mov d, d`, which emission drops. A spilled call argument
was reloaded into a scratch register and copied into the argument
register (`ldr x11, [sp, #k]; mov x1, x11`): rust-compression 776 such
pairs -> 156 (LLVM 142). std corpus -801 instructions (-0.19%),
frequency-weighted copies -2.2%. The first version broke two rafuzz seeds
(82467, 93016): the copy's destination was a fixed stack slot posing as a
register; both sides must now be plain registers (`PRegData::is_stack`)
and unpinned. regalloc2 checker clean on the std corpus and 400k rafuzz
seeds (the fuzz `Func` answers `pliron_move` under its copies hint, so
the ra2 leg exercises it; knob added to `harness/rafuzz.py`). Held-out
instructions within placement; compression cycles -3.0% over four
placement copies.

### `PLIRON_X30=3` (default): the link register in large leaves too

Mode 2 (x30 allocatable where a frame record exists anyway) plus leaves
of at least `PLIRON_X30_MIN` (256) instructions, which spill and set up a
frame record anyway (blake3's `compress_in_place` has `stp x29, x30` and
spills its message words). blake3 instructions -1.04%, cycles -2.0%
(real over 4 placement copies); html, json, pulldown, regex,
compression, protobuf within placement; blind-sig flagged a cycles loss
once (4 copies, range -1.1..+7.3%) and placement on an 8-copy rerun
(-1.84%). `Target::int_regs_alloc` does not count x30 under mode 3, as
measured.

## Measuring without callgrind

OrbStack is off (no windows), so no exact counts. Two things were
useful:

* `harness/placement.py heldout PROG --cand NAME:K=V --no-exact
  --copies 4|8`: macOS instructions and cycles over placement copies,
  with a verdict per program. Plain `ab.py` instruction deltas of
  +0.9..1.1% (html, pulldown under RELOADCOPY) were placement: the hot
  function's code was instruction-for-instruction identical, only
  addresses moved. A delta under ~0.5% on one `ab.py` run means nothing.
* `PLIRON_ALIGN=0` is not a "pads off" switch: it also clears the
  loop-head marks that keep `EDGEMERGE` off loop heads, so the code
  changes (compression +2M instructions). `PLIRON_LOOPALIGN=4
  PLIRON_ALIGN64=0` keeps the marks and emits no pads: executed loop pads
  are 0.3..0.8% of the held-out instruction counts.

## Where the gaps are (for the next session)

* html (+8%): spread. Per-line samples point at Vec field reloads
  (`raw_vec/mod.rs:635`), inline copies (our `copy_nonoverlapping`
  expansion; LLVM's time sits in `_platform_memmove`, which has no line
  rows), and the output sink: `<&mut dyn FnMut(&[u8]) as
  FnMut>::call_mut` takes 129 self samples (LLVM 3, it inlines the shim
  through thin-local LTO). The inliner rejects it as "external (no body
  in this CGU)" although `xcgu` emits copies of it into three CGUs; the
  callers (`Token::into_bytes`, `StartTag::serialize_self`, a dispatcher
  closure) are not in those CGUs. Worth finishing: about 1% of html.
  No in-block redundant loads (9 vs LLVM's 3 statically).
* compression (+3%): `BrotliCreateHqZopfliBackwardReferences` +17% self
  time. 1983 instructions against 1320: 68 conditional branches to panic
  blocks against 26, mostly the unrolled copies of three loops each
  keeping their bounds check (static only; one check per element either
  way), plus spills in a 9 KB frame. `FindMatchLengthWithLimit` is
  identical to LLVM's.
* blind-sig (+5% instructions, cycles at parity): the montgomery inner
  loops are 11 instructions, as LLVM's; the outer loop reloads `SmallVec`
  capacity fields seven times per iteration and keeps more bounds checks.
* blake3 (+1.7% after X30=3): `compress_in_place` is 914 instructions
  against 899, with fewer spills than LLVM; the rest is elsewhere.
* regex (+2%): the DFA's `match` trees (LLVM tail-duplicates the
  dispatch); small, scattered.
