# Fuzz seed 16787: sroa left a flow-reached by-value call arg unpinned

**Symptom.** The rustlantis program for seed 16787 segfaulted (rc 139) when
built with pliron at `-O`. Stock rustc ran it fine, and so did the pliron
`-O0` build. The bug was already on main at 42b49c8.

## Narrowing

- `PLIRON_DIFFCHECK=step` flagged `slotmerge` on `fn12`. This was a false
  lead: `fn12` returns a raw pointer to one of its own locals, and
  slotmerge moves that local. `PLIRON_SLOTMERGE=0` still crashed.
- `harness/fnbisect.py` (oracle: rc 139) gave `{fn9, fn10, fn12}`. With
  "any wrong result" as the oracle, `{fn9, fn10}` was enough.
- `PLIRON_OPT_BISECT` blamed `jumpthread` on `fn9`, the first CLIF unit
  after every sroa unit. But jumpthread's diff (dead params, constant
  `icmp`s, dead loads) was correct, and so was the edge-arg remap. The
  output also flipped when unrelated code changed: adding a print to
  `dump_var` hid the bug. That meant the program was reading garbage stack
  memory, not that jumpthread was wrong.
- An lldb watchpoint on the corrupted spill slot of `fn9` (the char handed
  to the first `dump_var`) caught `fn10` writing it through its first
  param, the `Adt22` it takes by value. `Adt22` is 176 bytes. In `fn9`,
  the memory passed for it (`ss22`) was only 32 bytes.
- `PLIRON_SROA_DEBUG=1p3fn9` on `fn9`'s `_5: Adt22` alloca: pinned slices
  only in `[0, 32)`. These came from the flow loads and stores through
  `_8 = &mut _5`. The call operand `Move(*_8)` was listed as `other@0w0F`,
  a flow `Escape`.

## Cause

`sroa::accesses_inner` classifies a call operand as `Kind::Escape` when
the callee can't tell it got a fresh copy (`copyable_arg`: rustc deduced
`captures(none)` on the Indirect param). The rewrite then gives the call a
copy of the whole alloca. The rewrite loop skips every `flow` access,
because a flow access is reached through a loaded-back pointer and its
operand resolves to `pin_a` once the pointer's slot promotes. So a flow
Escape got no copy. An Escape also pins no bytes in `slices()`, so `pin_a`
held only the slices that other flow accesses happened to touch. The
callee got a `pin_a` address and legally read and wrote the arg's full
176 bytes, 144 of them past the end of `pin_a`.

The wrong assumption: "Escape = fresh copy" holds only for non-flow
operands. Nothing made sure a flow operand's extent was in `pin_a`.

## Fix

A flow call operand is never classified as an `Escape`. It falls through
to the `Pin` arm. With a known extent (`CallInfo::arg_extent`: an Indirect
arg's layout, or a ref's pointee) it pins `[off, off + n)`, so the
existing pin machinery covers it. That machinery adds the cuts and gap
slices, sizes `pin_a`, and syncs around a nonretaining call. With no known
extent, the alloca isn't split.

## Evidence

- Seed 16787 now prints the stock hash. Seed 16782 also passes.
- `tests/sroa/flowpin.rs` (custom MIR, `-Zmir-opt-level=0`, in the `sroa`
  stanza) reproduces the bug in a few lines. `big` is written directly,
  `r = &mut big` is assigned twice so it stays in memory, the tag and one
  field are written through `r`, then `sum(Move(*r))` is called. Without
  the fix, SROA pins only `[0,1)` and `[8,16)` of 168 bytes, and `sum`
  returns garbage (-608610634767795579 instead of 2870). With the fix, the
  operand is `pin(arg0, n=168)` and the result is correct.
- Seed 16787 is in `FUZZ_REGRESS` (`harness/gate.py`).
