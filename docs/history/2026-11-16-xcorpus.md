# 2026-11-16: a differential check of the IR passes (`clif-check xcorpus`)

Nothing checked the pliron-IR passes; three `memcpyopt` miscompiles of
the day were each found by a whole program and a long bisect
(`2026-11-16-wasm-night.md`, "Architecture observations" item 1). The
CLIF interpreter that checks the CLIF passes can check them too, by
ablation: record two corpora of one build, one with the pass off, and
compare each function's two lowerings. How to run it and what it adds to
the checker: `docs/miscompile-triage.md`, "IR passes".

## What had to change in the checker

Each item was a false positive or a blind spot on the wasm kernels + std
corpus first; the commit messages of this branch have the cases.

1. **Names.** The stub key, `func_addr` and data regions went by
   `u0:<FuncId>`/`u1:<DataId>`, which two builds number differently. The
   recorder writes `; diffcheck-syms:` (all external names, data
   included: `diffcheck-names` had callees only) and the cross mode keys
   everything by symbol.
2. **Constant data.** With `constload` on, B holds a constant where A
   loads a symbol; seeded symbol memory made those differ.
   `; diffcheck-data:` records the image (bytes and pointer relocations,
   up to 4 KiB) of the immutable data each function names; both
   functions run with the union at the same addresses.
3. **`undef`.** The lowering writes 0 for `undef`, so A copying a
   temporary's never-written bytes stored zeros where B (memcpyopt
   forwarded the writes) left the destination's bytes: 10 mismatches on
   the memcpyopt ablation (btree `insert`, `Backtrace::capture`,
   `addr2line::find_location`, ...). `; diffcheck-undef:` lists those
   values; under the rerun's fill they take the fill, so the bytes are
   not pinned.
4. **Return area.** `parse_number` writes its `Option` payload only on
   the `Some` path in A; B's forwarded call writes the area on both. A
   byte of the `sret` area the original left untouched is not compared.
5. **What a callee reads.** `tests/mcrdwrap` with `PLIRON_MEMCPYOPT_RDWRAP=0`
   gave `ok` on all of 4,096 trials. The wrong value (the second
   iteration's `String` is a copy of `body`) only reaches callees, and a
   stub hashed a frame pointer without the bytes behind it. Now the bytes
   written so far in the window behind each pointer argument are hashed
   with the arguments (not an `sret` area: `tokenize::setup` reuses a
   `format!` result slot whose old bytes are dead), the second function's
   stubs replay the first one's windows and fill lengths, and a window
   ends at the end of the second function's object (sroa off keeps the
   whole aggregate around the field passed in the slot).
6. **Calls before a sandbox stop.** Still `ok` after 5: no trial that
   reached the loop's second iteration also returned (a `format!` result
   is three seeded words, and its length is a heap pointer half the
   time). When the original stops for the sandbox's reasons (a copy out
   of the sandbox, fuel) its calls up to there are compared, arguments
   the rerun under the other fill agrees on only. With it the bug is
   named at 64 trials (trial 18); after the fill change of item 5 below at
   trial 138, so `xcorpus` runs 256 by default (`report` keeps 16).
7. **Byte results and arguments.** `random_value` never returns 0 for a
   stub result, so every `write!(..)?` failed; and a `bool` of 46 or -1 is
   not one two functions must agree on (sroa off returned it as is, on as
   `46 & 1`; `vec![b; n]` tested `b == 0` against `b & 1`). In the cross
   mode a byte result is 0 or 1 (mostly 0) and a byte argument is 0 or 1.
   Stub fills are words a program can go on with (heap pointers, small
   integers) instead of 64 random bytes.
8. **Call sets.** `PLIRON_CONSTLOAD=0` also turns `devirt` off: B calls a
   vtable slot directly or inlines it where A calls through a pointer.
   The number of indirect call sites joins the callee set; a pair whose
   sets differ is skipped like an inlining difference.

9. **Made-up constants.** The backend names a constant it creates
   `__rcg_alloc.<n>`, numbered in declaration order, so the same vtable
   was two symbols in two builds. Per pair, such a symbol with a recorded
   image goes by its content, unless the other build names or points at
   it without an image (then the number is all there is, and the small
   corpora's builds agree on it).
10. **CGU copies.** A symbol recorded several times pairs its leftover
   copies only when they name the same symbols (a generic instantiated
   in two crates holds each crate's instances).
11. **Replayed fills.** A callee that fills its `sret` area fills all of
   it wherever it lives: the second function's stub writes the first
   one's length into heap memory too (memcpyopt sent `Expr::clone`'s
   result straight into the `Vec` buffer).

The sroa and constload mismatches are false positives as far as looked
at: `Assume::sub` and `vec![b; n]` branch on bytes of seeded memory or
arguments as `bool`s with values no program makes (0x80, -1); the
constload one (`io::error::Custom`'s `Debug`) traps on `unreachable` in B
where A reads a table, which is what an invalid enum tag does. Most of
the sroa ones (`RawVec::grow_one` instances, `String::try_reserve`, the
socket address parsers, `CString::new`, ...) were not diagnosed one by
one.

## Numbers: dsa (`harness/dsa/build.sh`, eval,squish,cad, 70,031 functions)

`PLIRON_MEMCPYOPT=0` against the default, final checker, every 4th pair,
64 trials (the full corpus at 256 trials takes hours): 17,510 pairs,
9,743 identical, 6,243 ok, 1,394 inconclusive, **24 mismatches** (0.4% of
the pairs compared), 7 skipped for calls, 98 ambiguous. With the
checker of a few hours earlier, all pairs: 110 of 24,954 compared.

The 24, by kind: 12 differ in bytes (`<[(FieldKey, Expr)]>::to_vec` and
its instances: the stub fills a 64-byte `sret` temporary where the real
`Expr::clone` writes its own size only; in A the tuple's other field was
written into the temporary before the call and the over-fill clobbers
it, in B, with the copy forwarded, it is written after. A stub modelling
error: the callee's object size is not recorded), 7 where B traps and A
returns, 3 in returned values or calls, 2 in a call before a sandbox
stop. Only the first class was diagnosed. **This check is not yet clean
enough on dsa to gate memcpyopt work by "no mismatch"; on the wasm
kernels + std it is.** A practical rule until then: compare the
mismatch list of a memcpyopt change with the list of the tree before it.

## Acceptance

  `tests/mcrdwrap` names `mcrdwrap::build` (call 5, `core::fmt::write`,
  reads `{cap 0, ptr 1, len 0}` in A and `body`'s header in B); the
  default against `PLIRON_MEMCPYOPT=0` is clean (256 trials).
- `PLIRON_MEMCPYOPT_DSTMARK=0` (new switch: the 7ee65e8 marker handling
  skipped): no small program was found that misbehaves with it
  (`tests/mcdstmark/main.rs` is the last attempt; its output is right
  with the switch). On dsa, b0 (default) against b-mark (switch on):
  70,043 pairs, 7,798 ok, 2 mismatches A/B and 3 A/piped B. One is
  `cadcore_union::arrange::universal::fuse_filaments_with`'s closure,
  piped only and gone with `PLIRON_SLOTMERGE=0`, the shape of the marker
  bug; but the same function also mismatches the default build against
  its own pipeline output in the cross mode, so it is not specific to the
  switch: either a live miscompile in the default build or a false
  positive, **not resolved**. The other two (`serde_json`'s
  `Number::serialize`) trap in B; b-mark keeps a slot and markers that
  b0 drops there, but the mechanism was not traced. So the marker case
  is not established as found.

## Evening follow-up: the open mismatches

**`fuse_filaments_with`'s closure (cadcore_union): the checker.** The
default build against its own CLIF pipeline output mismatched in the
cross mode only; a `PLIRON_PIPELINE` prefix put it on `slotmerge`
(step 81), which merges `ss0`, `ss16` and `ss12` onto `ss11` and drops the
now self-copy `ss11 -> ss12`. Before the merge `ss11+16` holds an `i32`
(0) and `ss11+20..24` is never written; an `i64` load of `ss11+16` goes
into `ss12+16` and `+32`, and `ss12` is the argument of a call. So the
callee gets four bytes of padding. Under the rerun's fill they are
`a5a5a5a5` in the original, so the original does not determine them;
after the merge they hold an earlier slot's bytes, the stub (whose
answer hashes what it is handed) answers otherwise, and the rewritten
run takes a panic path. `underdetermined` already forgave a returned run
that differs after such a call, but not one that traps. Now a run that
does not return is unpinned when it made the same calls up to the first
call the original hands an undetermined value (`6d71d90`, test
`trap_after_an_undetermined_call_argument_pins_nothing`, which fails
without the rule). Not a miscompile: the program's callee does not read
padding.

**`serde_json`'s `Number::serialize` under `PLIRON_MEMCPYOPT_DSTMARK=0`
(2): the checker, the same rule.** Call 1's second argument is an
integer made from a frame address (`0x8400ffff` in the original,
`0x84010fff` rewritten, `0x84034fff` under the rerun: the slots are one
page further because b-mark keeps a slot b0 drops), so it is
undetermined, the stubs answer differently and the rewritten run traps.
The checker at `5f818bb` reports both, `6d71d90` neither.

**`<[(FieldKey, Expr)]>::to_vec` (12 at 64 trials, a quarter of dsa):
the checker.** The recorder now writes `; diffcheck-sret:
<callee>=<bytes>` (the `sret` value's size from rustc's ABI,
`Exts::sret_size`) and the stub's fill through that argument stops there
(`01daf1f`, test `sret_fill_stops_at_the_returned_value`; its first
assertion is the case without the size).

With both, b0 against b-mark on the re-recorded dsa corpora (70,081
pairs, 64 trials): 7,797 ok, **0 mismatches**, A/B and A/piped B. So
the dst-marker switch is not found on dsa either (nothing in that corpus
misbehaves with it as far as the sandbox reaches).
